# Your first eval

An eval runs a skill's cases twice: once with the skill staged into a fresh sandbox, once without. The comparison is the point. It answers "does this skill change what the agent does", with a transcript for every arm you can read afterwards.

```sh
npx -y terum-skills@latest eval <skill>
```

`<skill>` is a folder name in your Library, or a path to one. Start with a skill you have installed and use.

## What it needs

**Claude Code, installed and logged in.** Before any paid work, `eval` runs `claude --version` and then one real one-turn agent task in a throwaway directory. A failure stops the run there, with the reason: "`claude` is not runnable (…) — is Claude Code installed and on PATH?" or "preflight agent task failed — check that `claude` is logged in and the model 'sonnet' is available: …".

**The folder in your Library.** That means Global (`~/.claude/skills`) or a project you registered with `project add`. Your working directory is not a Library root. A ref no root holds is refused without spending anything: "No local skill folder named `<name>` in your library; install it from the marketplace first, or pass the folder's path.", or, for a path, "`<path>` is not a skill folder in your library (~/.claude/skills or an added project's .claude/skills); add the project holding it with `project add`, or install it from the marketplace first."

**A team is optional.** `eval` evaluates a local folder, so a machine with no team still runs it. A team adds three things: the incumbent arm, the license policy that hygiene checks against, and a place to share the receipt.

## What the run does, in order

1. **Fetches the team clone**, when there is one.
2. **Reports hygiene warnings and dependencies.** Warnings never block; hygiene errors do, and the run ends with `Hygiene failed for <name>:` and the findings. Each file the SKILL.md points at outside its own folder is named: `Staging dependency <path>`, or `SKILL.md references <path>, which is not present here; the skill may not run`, or a line saying staging it would exceed the 20 MB cap.
3. **Asks about heavy mode**, but only when the skill looks like it calls subagents and you passed neither `--heavy` nor `--no-heavy`. It prints the evidence it found, then:

   ```
   This skill appears to call subagents, which can be expensive. Instead of
   running it once per case, this evaluation runs one session with the skill
   and one without, against a single fixture with many checks, to limit usage
   and wall-clock time. The verdict therefore rests on one session and will
   vary more between runs. To reduce variance, uncheck the box below; that
   runs the skill <N> times in sequence. If the run is interrupted or your
   usage runs out, it is marked unscored and must be run again.
   ```

   `<N>` is the number of authored cases the folder holds, or the word `each` when it holds none. The question is `Use the one-session heavy evaluation mode?`, defaulting to yes. The detector is static: a `metadata.eval.heavy` setting in the frontmatter decides outright, otherwise the first file naming the `Agent`, `Task` or `Workflow` tool, or containing `codex exec` or `claude -p`, is the evidence it prints. The one-session shape the notice describes is what an `evals/suite.yaml` does, authored in the folder or written by this run's generator, so a skill whose execution assets are cases runs them one at a time whichever way you answer.
4. **Runs the preflight** described above.
5. **Generates the assets that are missing**, unless you passed `--no-gen`. Only a missing asset is ever generated, so authored work is never overwritten. With no `evals/cases/` and no `evals/suite.yaml`, the generator picks the shape: one `evals/suite.yaml`, a world with planted defects for a skill that can be measured on what it found, or three to seven cases across five buckets. With no `evals/triggers.yaml`, five should-trigger plus five should-not-trigger prompts. The generated bytes are checked for hygiene before anything is written, and then written into your own skill folder, with this line printed first:

   ```
   Writing generated evals/cases/ and evals/triggers.yaml into <dir> — they were missing, so this run made them. That changes the skill's content: the next publish mints a new version and the current local eval score blanks. To regenerate, delete evals/cases/ and run eval again.
   ```

   One clause of that line overstates it. `evals/` is excluded from a skill's content digest, so generated assets travel with the skill without changing its identity: they do not by themselves mint a version at your next publish, and they do not blank the score for those bytes. Publish writes them into the team's `skills/<name>/evals/` either way. Everything else in the line holds: the files are now in your folder, and deleting the asset it names, `evals/cases/` or `evals/suite.yaml`, is how you ask for new ones.
6. **Runs the trigger eval**, when a triggers file exists. Each prompt is one tool-free model call that shows the model your Library root's skill names and descriptions and asks which it would select. There is no sandbox and no agent.
7. **Runs the cases.** Each case is seeded into a fresh sandbox (its fixture, its inline files, its `setup` script), then run once per arm per repetition. A suite, authored or generated, is seeded once per arm per repetition instead, and every one of its rows is scored against that one session.
8. **Prints the report.** It opens with two lines, `verdict: <VERDICT>` and `why: <one line naming what decided the baseline rows>`. When some rows never scored, the verdict carries its status in brackets, as in `verdict: NEUTRAL [partial — 4/6 scored]`. Below that come the win/loss/tie record per comparison, the arm scores, the passed case-runs per arm, the trigger numbers when a trigger eval ran, and one `efficiency:` line.
9. **Shares the receipt, or tells you why it did not.**

## How long, and how much

Each case runs the **baseline** arm (nothing staged) and the **candidate** arm (your folder). When the team already has a version of this skill with a receipt, an **incumbent** arm runs too, so three arms instead of two. The incumbent is the version with the most recent receipt, not the highest version number, and never a version whose bytes equal your candidate's.

| Knob | Default | Notes |
| --- | --- | --- |
| `--k <n>` | 1 | Repetitions per case. Total agent runs are cases × k × arms. Use `--k 3` or more for a receipt you intend to gate on. |
| `--model <model>` | `sonnet` | The model for every arm, for generation, and for the judge unless `--judge-model` overrides it. |
| `--judge-model <model>` | the run's model | Only cases that carry a `judge` rubric reach the judge. |

Every one of those runs bills your Claude account. The engine measures nothing itself: the turns, wall-clock and dollar figures on the `efficiency:` line are what Claude Code reported for each headless session, averaged over the scored sessions of that arm. Multiply by the cases and repetitions to get the run's total. When your team clone holds three or more usable receipts, setup's eval offer prints a measured estimate from their median; otherwise it says plainly that there is nothing to estimate from.

## Where the results go

```
~/.terum/skills/evals/local/<content-digest>/<runId>/
  receipt.json
  run.jsonl
  transcripts/<case>.<arm>.<rep>.jsonl
  sandboxes/arm-XXXX/
  generated/            (only when this run generated assets)
```

The tree is keyed by the digest of the bytes that were evaluated, not by a version or a team, so a skill that belongs to no team still has somewhere to record a run, and a receipt can later be matched to bytes rather than taken on trust. Transcripts and sandboxes stay on your machine, unredacted, for you to read.

A receipt is also committed to the team when, and only when, the bytes you evaluated are already a published version of that skill: the run then prints `Published this receipt to <team> for Version N of <skill>.` and the file lands at `evals/<skill-id>/<version>/<runId>.json` in the team repo, never overwriting an existing one. Anything less than an exact byte match shares nothing. A failed share is reported and never fails the run: "The eval is complete and saved locally, but publishing its receipt failed: …". `--no-commit` keeps the receipt local and suppresses the hint below.

When nothing was shared, the run ends with the reason and the next step. The line is printed only when there was somewhere to share to: you are joined to a team, you did not pass `--no-commit`, and the run produced results. A machine with no team sees none of it.

```
These bytes are not a published version, so nothing was shared. To share these results, publish the skill again: npx -y terum-skills@latest publish <skill>
```

On a FAIL verdict it says the opposite of "publish this":

```
These bytes are not a published version, so nothing was shared. This run's verdict is FAIL: evaluate a fix rather than publishing these bytes — npx -y terum-skills@latest publish <skill> asks before it publishes a failed verdict.
```

## Cheap first looks

| Command | What you get |
| --- | --- |
| `eval <skill> --triggers-only` | Only the trigger eval: would a model reading descriptions pick this skill for these prompts. No sandboxes, no arms, no agent sessions. |
| `eval <skill> --case <stem>` | One authored case, by its file stem. An authored `evals/suite.yaml` is skipped with a printed line, because a suite session can run for a long time. |
| `eval <skill> --no-gen` | No generation. The run uses only the assets the folder already has, and nothing is written into your skill folder. |

`--triggers-only` and `--execution-only` cannot be combined.

For what the arms, the verdict band and the receipt fields mean, read [how evaluation works](../evaluating/overview.md). For the batch, queue and overnight modes, and every flag, read [running evals](../evaluating/running-evals.md).
