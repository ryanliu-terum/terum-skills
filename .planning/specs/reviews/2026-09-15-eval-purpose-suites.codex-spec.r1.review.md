## Internal quality

- [ ] **BLOCKER — Generated suites commit and expose their own answer key**
  - **Location:** §3.3 lines 146–148; §4.1 lines 299–307
  - **Evidence:** The spec claims “the answer key never enters the sandbox” (lines 146–148), but materializes probes as `.probes/*` and the patch as `.plants.diff`, then runs `git init -q && git add -A ... commit` before deleting them (lines 299–307). Their deletions therefore appear in the uncommitted diff, and their original contents remain readable from `HEAD`; `.plants.diff` directly reveals every planted defect.
  - **Fix:** Exclude `.probes/` and `.plants.diff` from the base commit, or create them only after committing the clean base. Add an exit test proving neither working-tree diffs nor Git objects expose them to an arm.

- [ ] **AMBIGUITY — Heavy mode has incompatible session semantics**
  - **Location:** §5 lines 329–363; §10 lines 496–501
  - **Evidence:** The spec says heavy detection decides sessions while assets remain whatever shape generation produced (lines 329–346), and explicitly says case-shaped heavy skills still run one session per case (lines 346–347). The locked notice instead says the evaluation runs one session total against one fixture (lines 357–360), while §10 says unchecking switches to “k-per-case mode with the skill’s authored/generated cases” (lines 500–501). A suite-only skill has no independent case assets, and a case-shaped skill never had the advertised single-fixture mode.
  - **Fix:** Specify exact execution algorithms for suite-shaped and case-shaped assets, including what the CLI confirmation changes, how X is calculated, and shape-specific notice text.
  - *(Overlaps the build-readiness AMBIGUITY below on the "unchecking → k-per-case" contradiction; kept separate because the two findings ask for different things — execution semantics here, selection precedence there. Resolve them together.)*

- [ ] **AMBIGUITY — Dependency staging both includes and excludes sibling helpers**
  - **Location:** §6.1 lines 390–397
  - **Evidence:** For a referenced script, the spec requires copying its “parent directory” because engines import sibling helpers (lines 390–392), then immediately excludes “anything the token itself does not name” (lines 393–394). Sibling helpers are precisely files the script token does not name, so the two rules produce different staged trees.
  - **Fix:** State that parent-directory expansion is an explicit exception to the named-token rule, then define whether it is recursive and which exclusions and byte-cap accounting apply.

## Build-readiness

- [ ] **AMBIGUITY — Heavy-mode selection does not define an implementable state machine**
  - **Location:** §5, lines 338–350; §10 item 5, lines 500–501
  - **Evidence:** The spec says, “From the second run the mode is measured, not guessed,” but does not say which prior run or arm supplies the observation. It also says a heavy suite uses one session, while unchecking runs the skill X times and §10 calls that “k-per-case mode with the skill’s authored/generated cases.” A suite-only skill has shared fixture/task plus sub-case checks, not independent cases to run per-case.
  - **Fix:** Specify precedence and lookup precisely: author override, CLI override, prior observation keyed by skill/content digest, then static scan; identify which arm/repetition sets `spawns_agents` and how incomplete runs behave. Define exactly what `--no-heavy` does for a suite-only asset and how X and k are computed.

- [ ] **GAP — Suite rows lack a collision-free identity and an aggregation marker**
  - **Location:** §3.2 lines 131–142; §3.5 lines 173–174; §7 lines 446–453
  - **Evidence:** The spec makes each sub-case name “the per-case key,” permits ordinary cases and suite.yaml together, and requires sign_p = 1.0 for any run containing a suite. It never requires names to be unique across suite sub-cases and ordinary case stems or says how aggregate knows a row came from a suite. Current `perCaseRows` keys entries only by case name plus repetition (`src/lib/evals/results.ts:127-151`), and `aggregate` receives no suite marker (`results.ts:75`).
  - **Fix:** Define an internal suite/sub-case identity or namespacing rule, validate uniqueness across all selected assets, and specify how suite presence reaches aggregate—such as an explicit hasSuite argument or row marker. Cover mixed suite/case runs and duplicate names.

- [ ] **GAP — Generated suite write-back has no crash or rerun contract**
  - **Location:** §4 lines 230–232 and §4.1 lines 314–319
  - **Evidence:** The spec says the suite is “materialized to suite.yaml” through the existing author flow, but does not name the persistence functions or define ordering when suite.yaml and triggers.yaml are generated together, pre-existing/case-insensitive collisions, partial failure, or rerun behavior. The existing safe path is specifically implemented across `GeneratedAssets`, `generatedFileMap`, `writeGeneratedAssets`, `generatedAssetLabels`, and `saveGeneratedAssets` (`src/commands/eval.ts:429-525`).
  - **Fix:** Require suite.yaml to participate in that staged-rename path, define per-asset landing order and failure reporting, guarantee no overwrite of authored assets, and state what the next run regenerates after an interruption.

## Contested (split verdict — needs human adjudication)

- **BLOCKER — Censoring candidate-caused failures can produce a false PASS** *(internal quality; findings[6])*
  - **Location:** North Star lines 9–11; §2.2 lines 82–99
  - **Evidence:** The spec makes every candidate timeout or non-zero exit an unscored tie and computes the verdict from scored rows only (lines 82–90), asserting that “a kill or a crash… say nothing about the skill” (lines 92–95). That premise is false: a candidate can cause its own timeout, exhaust turns, or crash while the baseline completes. With no minimum coverage rule, one surviving win and many candidate failures can still band PASS, contradicting the requirement that PASS mean the skill did its job better than the bare agent.
  - **Suggested fix if upheld:** Distinguish demonstrated infrastructure failures from candidate-specific failures. Treat the latter as losses or invalidate the receipt, and require a minimum scored-row coverage before PASS is possible.

- **BLOCKER — The generator prompt gives impossible file-count rules for document and session-log suites** *(internal quality; findings[8])*
  - **Location:** §4.0 lines 187–205; §4 lines 207–214; §4.1 lines 253–275
  - **Evidence:** Document-audit and session-handoff skills must receive suites (lines 190–191), and the prompt says a spec or log is “a single file” (lines 253–254). The same prompt requires 3–6 source files and defects “spread across at least 2 files” (lines 269–275), matching the global contract at lines 207–214. A compliant result for those two declared shapes cannot exist.
  - **Suggested fix if upheld:** Define separate validation profiles: repository suites may require 3–6 files and multi-file spread, while document/log suites permit one seeded file and use domain-appropriate planted faults and probes.
