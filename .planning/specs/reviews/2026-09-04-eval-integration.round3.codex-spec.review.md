## Verdict

This was a cross-model run: the **finders were OpenAI Codex (gpt-5.6-sol, effort high)** and the **verifiers were a 2-vote Claude adversarial panel** — the mirror image of a same-model `/ultraspec` pass, so the confirmed count and severity mix here are not comparable to an `/ultraspec` report on this spec. Ten findings survived at 2-0; after merging duplicates the confirmed set is eight. Severities below are **panel-adjusted**, with the finder's original label shown inline where the verifiers recommended a change. Two clusters carry the run. First, the "authoritative, frozen" hygiene contract that IE1 delegates to eval-engine §9 is **not implementable as written**: HYG4 must reject files with the exec bit set but the frozen API is `Map<string, Buffer>` and the named producer stores only path and bytes; HYG2's mixed-script rule both permits and rejects `pаypal`; HYG3's email predicate names no matcher at all, and it is the predicate that decides whether private email data enters the team repo. Second, the publish receipt gate at IE4 is wrong in both directions at once — it never requires the incumbent comparison to be not-FAIL (so a FAIL receipt publishes) while requiring a comparison that the engine says is absent for new skills (so no skill can ever be published for the first time). Around those sit three staleness items, the largest being that the target's §0 inventory claims to state the missing work "precisely" and its §2 says VE2 "is the only one still open", while eval-engine §17 explicitly assigns **nine unfixed engine defects to the IE milestones** — none of them scheduled. Recommended sequencing: unfreeze and repair the three hygiene predicates and the receipt-gate predicate before any of this is handed to `/codex-implement`, then schedule the §17 defect register into IE1–IE4, then clean the three cross-spec echoes. Note a degraded run: the `internal quality` and `build-readiness` finder agents both timed out at 600000ms, so those two dimensions are partial — absence of further findings there is not evidence of health.

## Internal quality

- [ ] **BLOCKER — The hygiene API cannot implement HYG4's executable-bit check**
  *Merged: findings[16] (internal quality, BLOCKER — verifiers suggested GAP) + findings[21] (build-readiness, BLOCKER — verifiers suggested BLOCKER). Both confirmed 2-0. Same defect found independently from two dimensions, so both evidence blocks are reproduced. Merged severity is BLOCKER, the panel-adjusted label of the stronger of the two.*
  **Location:** §1 IE1, lines 41–47 and 99–104
  **Evidence (findings[16]):** The target delegates the “authoritative” HYG1–HYG6 contract to eval §9 and says the implementation scans the same input at every call site. That delegated API is `files: Map<string, Buffer>` (`2026-09-04-eval-engine.md:414-423`), but HYG4 requires failure when “Any file has the exec bit set” (`2026-09-04-eval-engine.md:430`). Buffers contain no file-mode metadata, and the named `sourceFiles` producer stores only path and bytes (`src/commands/share.ts:252`). Because inspection must remain pure, it cannot recover modes with `stat`. The target’s fixtures test a shebang but contain no executable-bit-only case, so an implementation can silently omit this safety predicate while passing the stated exit suite.
  **Evidence (findings[21]):** The target delegates to “the `inspectHygiene` API” and requires an “allowlisted vs denied extension, and a shebang file with an allowlisted extension (HYG4 hit)” test. Authoritative eval §9 defines `files: Map<string, Buffer>` (`eval-engine.md:414-416`) while HYG4 must reject when “Any file has the exec bit set” (`:430`). The existing `sourceFiles()` supplies only path and bytes (`src/commands/share.ts:252`), so mode information is irretrievably absent.
  **Suggested fix:** Change the file-map value to include content and normalized mode — e.g. `Map<string, {content: Buffer; mode: number}>` — populate it from author trees and Git trees, name the `sourceFiles()` change that captures `stat.mode`, and add an allowlisted, non-shebang file whose executable bit alone produces HYG4, plus collocated tests for executable/non-executable files with identical bytes.

- [ ] **BLOCKER — The publish receipt gate neither enforces not-FAIL nor permits first publication**
  *Merged: findings[17] (internal quality, BLOCKER) + findings[25] (build-readiness, BLOCKER). Both confirmed 2-0 with no suggested downgrade. Same defect from two dimensions; both evidence blocks are reproduced. Closely related to contested findings[7], which is listed below and NOT counted here.*
  **Location:** §1 IE4, lines 158–166
  **Evidence (findings[17]):** The required check is triggered only on `publish/`-prefixed branches and merely requires a current, schema-valid receipt that “includes a candidate-vs-incumbent comparison”; the text never requires that comparison to be non-FAIL, despite calling this “the incumbent regression gate.” The authoritative lifecycle rule requires the comparison to be not-FAIL (`2026-09-04-eval-engine.md:283-294`). Conversely, the target’s unconditional comparison requirement cannot be met for a first publication: the authoritative receipt shape says that comparison is “absent for new skills” (`2026-09-04-eval-engine.md:211-216`), and its acceptance suite confirms “new skill: no incumbent comparison” (`:541-548`). Branch-prefix triggering also lets an otherwise valid PR that adds an endorsement in `team.json` under another branch name skip the only deterministic publish gate.
  **Evidence (findings[25]):** The CI rule only requires a receipt that “parses against `receiptSchema` and includes a candidate-vs-incumbent comparison.” It never states how CI enforces eval §6.1’s required “not FAIL” result. `receiptSchema` stores only W/L/T, `net_lift`, and `sign_p` per comparison (`src/lib/evals/receipt.ts:32-38`), while the documented verdict bands apply specifically to candidate-vs-baseline (`eval-engine.md:561-569`).   **Suggested fix:** Define a pure, named receipt-gate function and the exact comparison verdict calculation. Trigger on endorsement additions in the `team.json` diff rather than the `publish/` branch prefix. For a skill with a prior distinct version, require candidate-vs-incumbent and a verdict that is not FAIL; define and allow an explicit no-incumbent state for first publication, e.g. gating a new skill on candidate-vs-baseline. Add adversarial tests for FAIL, threshold boundaries, partial receipts, missing incumbent, and hand-crafted but schema-valid receipts.
