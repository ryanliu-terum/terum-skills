## Verdict

This spec is not yet safe to hand to `/codex-implement`. The finders were **OpenAI Codex** (gpt-6-astra, high effort) and the adversarial verify panel was **Claude** — the mirror image of an `/ultraspec` run, so a reader comparing this report to `/ultraspec` on the same spec should expect a different finder blind-spot profile, not a different spec. Every confirmed finding carried the panel 3-0. The dominant defect is structural and was found independently three times from three different dimensions: new guard row j (§4.2:285) enumerates only the migration's *destination* paths, so the layout-2→3 migration described in §13 — which deletes `skills/x/SKILL.md`, moves hash-keyed receipts out of their original paths, and rewrites every `people/<handle>.json` — is refused by the guard it is required to pass, for every populated team. Second is an identity split: §5.1 injects `metadata.terum-category` into the in-memory SKILL.md *before* the candidate digest while `canonicalSkillMd` retains category, so evaluating a plain local folder and then publishing it unchanged yields two different digests and silently attaches no receipt, which also collides with the once-only classification contract in `2026-09-10-auto-category.md`. The remaining confirmed items are smaller but still block a clean build: install records keyed by ID alone cannot represent the same skill installed globally and into a project (contradicting RM-03 in the phase-1 spec), the "every folder is a card" promise is defeated by two existing filters the spec does not delete, `installs: 0` is assigned to a `string` field, and incumbent selection asks for a version ordinal that an unpublished local candidate does not have. Note: the panel down-graded findings[0] from BLOCKER to DRIFT; severities below are the verifier-suggested ones.

### - [ ] BLOCKER — Migration guard excludes required deletions and people-file rewrites
**Location:** `.planning/specs/2026-09-11-library-marketplace-refactor.md:285` (§4.2 row j), §13:744–748

**MERGED:** this entry combines three separately-raised findings that describe the same defect from three dimensions — findings[9] (spec-vs-code reality, "Migration guard excludes required deletions and people-file rewrites"), findings[15] (internal quality, "The migration guard rejects the migration's own diff"), and findings[20] (build-readiness, "The migration guard rejects the migration's required deletions and people-file updates"). All three carried 3-0. Their evidence is reproduced in full below.

**Evidence (verbatim, findings[9]):**
> §4.2:285 says permitsMigration admits skill paths matching `^skills/[^/]+/(v1/.+|evals/.+)$` and receipt destinations under `v1` or `archive`; it admits no people paths. Yet §13:744 requires moving “all of its current contents” into v1, §13:746 moves existing tree-hash receipts, and §13:748 requires rewriting “each people/<handle>.json”. Existing src/lib/teamRepo.ts:324 implements removal as `overlay.set(path, undefined)`, and :320–321 includes those deleted paths in changedPaths; :198 calls `guard(tree, options)` before applying changes. src/lib/guard.ts:46 checks every changed path and :54 throws on unmatched paths. Consequently, deleting skills/x/SKILL.md or an old evals/<uuid>/<40-hex>/<run>.json, and rewriting any people file, fails the prescribed migration guard. This is an incompatibility with the existing write mechanism, not a finding that migration is unbuilt.

**Evidence (verbatim, findings[15]):**
> §4.2 line 285 admits skill paths matching `skills/[^/]+/(v1/.+|evals/.+)` and receipt paths containing `v1|archive/...`. But §13 requires moving “all of its current contents” into v1, moving existing hash-keyed receipts, and rewriting “each people/<handle>.json”. The resulting deletions of `skills/x/SKILL.md`, `skills/x/scripts/...`, and `evals/<uuid>/<hash>/<run>.json` match neither migration regex. People paths are also absent, and line 283's PEOPLE_ACTIONS excludes migrate. Consequently even an ordinary populated team cannot pass the specified guard.

**Evidence (verbatim, findings[20]):**
> §4.2 line 285 admits migration skill paths only matching `skills/[^/]+/(v1/.+|evals/.+)` and receipt paths under `v1` or `archive`. But §13 line 744 requires moving “all of its current contents” into v1, which deletes paths such as skills/x/SKILL.md and skills/x/scripts/run.sh; line 746 also moves receipts out of their original hash paths. None of those deletions matches row j. Line 748 additionally requires “Rewrite each people/<handle>.json's installed[].version”, while row j omits people files and line 283 excludes migrate from PEOPLE_ACTIONS. The existing guard iterates every changed path and otherwise throws (`src/lib/guard.ts:46–54`).

**Suggested fix (union of the three):** Define `permitsMigration` over the *complete* transformation — original-path removals, corresponding destination additions, and all required people-file rewrites — and add `migrate` to `PEOPLE_ACTIONS` (or an equivalent people row). Test a complete layout-2 migration diff through `safeWrite`, including removals and multiple members' people files, rather than testing destination additions alone.
