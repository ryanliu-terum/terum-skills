## Verdict

This run inverts the usual panel: the **finders were OpenAI Codex (gpt-5.6-sol, effort high)** and the **verifiers were Claude** (2-vote adversarial), so a reader comparing this against an `/ultraspec` run on the same spec is comparing a different finder population, not just a different seed. The result is lopsided by design: almost every confirmed finding is `[M1 landed]` spec-vs-code drift, i.e. the spec text describing milestone M1 no longer matches the code that shipped at c3f2181 / PR #199. Five of those drifts are genuine contract decisions the spec must now ratify or reverse — `localMatch`'s fourth value `'none'`, ledger-before-byte-match version precedence (which also makes the spec's "cannot occur" state reachable), Marketplace `installedVersion` multiplicity, Publish gating outside state 4, and `mine`-less attribution on equal receipts — and each needs an explicit "spec follows code" or "code follows spec" call, not a silent tidy. Two are pure implementation debt where the code should follow the spec (the `.card-version` wrap unit, the mock scenario coverage). One is housekeeping (parent spec is pinned to rev 3 against a rev-10 parent). On the unbuilt M2 side only two findings survived verification: the `install --adopt` crash window, which is a real durability hole against the parent's self-drain contract and must be specified before implementation, and the project-add reconcile scoping/ownership gap. Net: **M1's §3–§4 text needs a reconciliation pass before this spec is locked for `/codex-implement`, and M2's §4.5/§5 M2.4 need the recovery and scoping contracts written.**

- [ ] **DRIFT — [M1 landed] Library version derivation gives the ledger precedence over the byte match, and the "cannot occur" state is reachable** (findings[6] + findings[10], merged)
  - **Location:** §3.1 lines 117–130; §4.3 line 218; §5 M1.3 lines 279–282
  - **Evidence (findings[10]):** The spec says the Library states are “read top to bottom, first match wins” and state 1 is `matchedVersion !== null` → `Version K`.   - **Evidence (findings[6]):** The spec says a row with `matchedVersion !== null` uses `Version K`, then claims `edited === true` “cannot occur” in that state and mandates a problem plus state 2 if it does. - [ ] **DRIFT — [M1 landed] Marketplace installedVersion uses consensus/aggregation, not the spec's single-entry rule** (findings[7] + findings[12], merged)
  - **Location:** §3.2, lines 143–146
  - **Evidence (findings[7]):** The spec derives `installedVersion` from the ledger “when exactly one ledger entry for this uuid+team exists,” otherwise from “the matchedVersion of the single on-disk row.” The landed adapter instead accepts any positive number of ledger entries when all versions agree (`recordedVersions.length > 0 && recordedVersions.every(...)`) and otherwise accepts one distinct matched version across potentially several rows at `desktop/src/backend/tauri/index.ts:243-251`. Multiple same-version entries or copies therefore produce a version where the written contract requires the fallback or `null`.
  - **Evidence (findings[12]):** The spec requires the ledger version “when exactly one ledger entry” and otherwise the match from “the single on-disk row.” Landed code accepts any non-empty set of same-version ledger entries (`recordedVersions.length > 0 && ...every`) and any number of rows whose distinct matched-version set has size one at `desktop/src/backend/tauri/index.ts:245-253`.   - **Suggested fix:** Choose and document one multiplicity contract.   - **Direction:** the spec should follow the code for the unanimity rule (two placements at the same version is not ambiguity), but the `localMatch:'identical'`-on-partial-match sub-claim in findings[12] is a separate call and reads like a code bug — decide it explicitly rather than folding it into the ratification.
