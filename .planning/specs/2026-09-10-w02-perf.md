## 0. Summary

1. Every action in the desktop app is N **sequential** short-lived `node` processes; each pays a fixed
   ~150–190 ms on Linux (83 % of a hot verb) and an estimated ~450 ms on the reporter's Windows box.
2. Inside those processes the work is also sequential: `ls --local` is ~230–300 filesystem ops in series per
   root (47 of them the *same* redundant `realpath`), `status` starts `git` then `gh` one after the other and
   (since `6634d0a`, unreleased) makes a **live GitHub API call on every screen render**.
3. The adapter's read cache is thrown away on **every window focus** — twice, from two different code paths —
   so alt-tabbing re-runs the whole chain from cold.
4. `install` waits for an extra `git fetch` + `git reset --hard` **after** its push already succeeded, and the
   app shows the user nothing at all for the 5–9 s it takes.
5. This batch makes six independent, additive reductions (R1–R6). Nothing here changes what the app *shows*,
   except one new progress line inside a dialog that is already open. The mock backend is not modified at all.

## 3. Decisions taken

Every fork below is closed. Do not re-open one; do not ask.

**DECISION D1 — `skill()` parallelisation shape.** Replace the sequential `inventoryTeam` → `ls --team` →
`ls --local` head with `Promise.all([inventoryTeam(...), cached(['ls','--local'], ...)])`, then `ls --team`,
then `Promise.all([validate, evalReport])`. Depth 5 → 3. Why: `ls --local` depends on nothing in the team legs,
and `validate`/`eval-report` depend only on `row.name` + the team. Contract C4 forbids restructuring `skill()`
beyond wrapping independent spawns in `Promise.all`, because batch `w03w04-skill-routing` rewrites this function
in the same window; this change is exactly that and nothing more.

**DECISION D2 — the recorded spawn ORDER changes for `skill()`, and two tests must be updated.**
`cliRun` (`desktop/src/backend/tauri/run.ts:156`) defers the spawn by exactly one microtask chain of fixed
length, so spawns are recorded in the order `cached(...)` was *called*, and `Promise.all` calls its members in
array order. Putting `inventoryTeam` first in the array keeps `status --team acme` first, but `ls --local` now
moves ahead of `ls --team acme`. `desktop/src/backend/tauri/__tests__/index.test.ts:298` and `:314` are ordered
array assertions and **must be updated** (see §7). This is declared under contract C9 as a required test change:
the assertions' intent (five spawns / three spawns, and no `validate`/`eval-report` on the unknown-name path) is
preserved exactly; only the order in the literal changes.

**DECISION D3 — `library()` keeps its recorded spawn order and its error precedence.** Start
`cached(['ls','--local'])` FIRST in the `Promise.all` array, `libraryTeam(team, options)` second, then check
`local` before `enrichment`. Recorded order stays `[['ls','--local'],['status','--team','acme'],['ls','--team','acme']]`,
so `index.test.ts:293`, `:362` and `:504` pass unchanged. Cost accepted: when `ls --local` fails, `status` is now
also spawned (one extra process on an already-broken path). That is the conservative trade — it costs one
process on an error path and saves one full process-start on every Library render.

**DECISION D4 — `localSkill()` is NOT parallelised at its head.** `desktop/src/backend/tauri/index.ts:556`
calls `libraryTeam(undefined, options)` only *after* a matching section/row is found. Hoisting it would spawn
`status` for a path that is not in the Library and break
`desktop/src/backend/tauri/__tests__/skill-detail.test.ts:59` and `:119`, which assert
`expect(f.spawns.map(spawn => spawn.args)).toEqual([['ls','--local']])`. Only its `validate`/`eval-report` pair
is parallelised (D5). Depth 5 → 4.

**DECISION D5 — `validate` ‖ `eval-report` in both `skill()` and `localSkill()`, accepting one extra spawn on
the validation-failure path.** Both are started, then `validation` is checked first so the early return's error
text and `reason` are byte-identical. When validation is unreadable the app now also spawns `eval-report` and
discards it. That is one bounded extra process on a failure path, in exchange for removing a full process-start
from the common path. Array order `[validate, evalReport]` preserves the recorded order in
`index.test.ts:298` (after D2's reorder of its head) and `:698`.

**DECISION D6 — `catalog()` uses `mapWithConcurrency(members, 4, …)`, returns results in ROSTER order, and
reports the LOWEST-INDEXED failure.** `desktop/src/backend/tauri/__tests__/index.test.ts:439` pins fail-fast
error text (`'Unreadable member.'`). A concurrent map that reported the first-to-settle failure would make that
text nondeterministic on Windows, where spawn ordering is noisier. Limit 4, not 8: the Rust bridge caps children
at 8 (`desktop/src-tauri/src/lib.rs:28`) and refuses the 9th; 4 leaves headroom for the Shell's own `status` +
`ls --local`, an in-flight `ls --team`, and a mutation the user starts mid-render. A finished child also holds
its slot until the 25 ms reaper poll, so the effective cap during a burst is slightly below 8.

**DECISION D7 — on the bridge's cap message, `mapWithConcurrency` retries the item ONCE.** The message reaches
the caller **wrapped**: `desktop/src/backend/tauri/run.ts:171` produces
`Could not start terum-skills: too many pending terum-skills processes (8); wait for one to finish`. Match the
**substring** `too many pending terum-skills processes`, never the whole string. Retry once, after the next
in-flight item settles. A second failure is a real failure.

**DECISION D8 — R2 preserves `canonicalParentPath`'s `undefined` failure value.** `local-skills.ts:112` is
`await realpath(root).catch(() => root)` — it falls back to the **non-canonical** root — whereas
`canonicalParentPath` returns **`undefined`** when `realpath` throws, and the comparisons at `:123-125` are
written to fall back to exact `resolve()` matching when `canonical` is `undefined`. Replacing
`canonicalParentPath(path)` with `join(canonicalRoot, name)` would feed a non-canonical path into comparisons
against canonicalised ledger references and could mis-match. Resolve the root once into `string | undefined`
and derive both values from it (exact code in §4.1).

**DECISION D9 — the per-folder scan is parallelised with limit 8 and stays order-stable and per-item
fault-tolerant.** `localSkills` pushes entries in sorted `names` order and its `try/catch` is per iteration; a
naive `Promise.all` would reject the whole batch on one bad folder. The per-name function keeps the existing
`try/catch` verbatim and returns `LocalEntry | null`; results are collected into a pre-sized array by index and
filtered, so output order is byte-identical.

**DECISION D10 — `status --permissions` is an opt-in flag; only `roster()` passes it.** The GitHub collaborator
lookup runs **only** with the flag; without it `admin` is emitted as absent (so the app's
`memberMetadata` schema at `index.ts:35` maps it to `null` = "unknown", the already-documented value).
Why this and not a CLI-side TTL cache of the lookup: a cache would keep a *permission* fact on disk with a
staleness window and needs invalidation on `invite` and `team remove`, whereas the flag restores `status`'s own
documented promise ("Offline local team summary", `status.ts:41`) with no new persistent state. Accepted cost,
counted: `roster()` gets a different argv, so the Share tab no longer shares the Shell's `['status']` cache
entry and goes from 2 processes to 3; every other surface (Shell, Library, Skill, Settings, Marketplace) drops
one `gh.exe` start (~300 ms on Windows) plus one TLS round trip (300–1500 ms) per render.
`catalog()` keeps plain `['status']`: only `desktop/src/screens/share/ShareScreen.tsx:74-77` draws the
permission chip, and it reads `roster()`.
This is the one deviation in this batch that changes what a frame carries for a caller that does not pass the
flag, so `docs/frame-protocol.md:72` is edited in the same commit (§4.7) and it is listed in §13 for Ryan's
confirmation as the CLI owner. It does **not** bump the protocol: the field's type is unchanged and `null`
keeps meaning exactly "unknown".

**DECISION D11 — `adminLogins` gets a 10 s deadline.** `src/lib/runner.ts:65-74` supports `deadlineMs` and
resolves with `code: 124` on expiry; `adminLogins` already returns `null` for any non-zero code. A hung
`gh api` on a flaky network must not park the Share tab forever. Constant: `ADMIN_LOOKUP_DEADLINE_MS = 10_000`.

**DECISION D12 — R4 is stale-while-revalidate, and it changes BOTH focus clears.** The focus listener
(`index.ts:367`) and `refreshLaunch()` (`index.ts:487`) both switch from `clearReads()` to `markStale()`.
`refreshLaunch` still re-reads the launch state eagerly (`stateOnce = undefined`, `generation++`); marking the
read cache stale gives the same eventual correctness with an instant first paint. `notify()`'s `clearReads()`
stays **exactly as it is** — after the user's own action the app must never show the pre-action value.
This is licensed by decision ledger `.planning/decisions/2026-09-08-m7-takeover-decision-walk.md`, Decision 10,
Zoom-out line (`:222`): *"Serves the North Star: a stale board is a previously true board and is refreshed the
moment the person looks."* R4 adds **no timer** and does **not** poll, so the sync addendum's "never sync on a
timer" rule (`:229`) is untouched.

**DECISION D13 — a failed background refresh DROPS the entry and broadcasts.** `sharedRead` today deletes a
failed entry (`index.ts:400`) and `read-cache.test.ts:79-84` asserts "a failed read is not kept". If SWR kept
serving a stale success whose refresh had just errored, the app would be showing a value the CLI can no longer
confirm, silently. On a failed refresh: delete the entry, then broadcast, so the next read surfaces the CLI's
own error.

**DECISION D14 — the "value changed" broadcast must NOT call `notify()`.** `notify()` calls `clearReads()`
(`index.ts:368`), which would throw away the entry that was just refreshed *and* every sibling, re-spawning the
whole chain and inverting the fix. Introduce a listener-only `broadcast(...)` and have `notify` call it after

### 4.2 `src/lib/concurrency.ts` — NEW (R2), full contents

```ts
/**
 * Bounded-concurrency map for latency-bound work (W-02). Results come back in INPUT order, never in
 * completion order, so a caller's output stays byte-identical to the sequential loop it replaces.
 * On a rejection it stops starting new work, waits for what is already in flight, and then rejects
 * with the first (lowest-indexed) reason — no dangling rejection is left unhandled.
 */
export async function mapWithConcurrency<T, R>(items: readonly T[], limit: number, fn: (item: T, index: number) => Promise<R>): Promise<R[]> {
  const width = Math.max(1, Math.floor(limit));
  const results = new Array<R>(items.length);
  const failures = new Map<number, unknown>();
  let next = 0;
  const worker = async (): Promise<void> => {
    for (;;) {
      if (failures.size > 0) return;
      const index = next++;
      if (index >= items.length) return;
      try { results[index] = await fn(items[index]!, index); }
      catch (error) { failures.set(index, error); return; }
    }
  };
  await Promise.all(Array.from({ length: Math.min(width, items.length) }, worker));
  if (failures.size > 0) throw failures.get(Math.min(...failures.keys()));
  return results;
}
```

Notes for the implementer: `Array.from({length: 0})` gives no workers, so an empty `items` resolves to `[]`
without calling `fn`. `limit` values of `0`, `-1`, `NaN` and `1.5` all collapse to at least 1 (`Math.max(1, …)`;
`Math.floor(NaN)` is `NaN` and `Math.max(1, NaN)` is `NaN` — therefore write it as
`const width = Number.isFinite(limit) ? Math.max(1, Math.floor(limit)) : 1;`). **Use that form.**

This file duplicates `desktop/src/backend/tauri/concurrency.ts` (§4.9) on purpose: the root package and
`desktop/` are separate npm packages with separate tsconfigs and no shared module path. "One path per behaviour"
binds within a package.

### 4.12 `src/lib/package-root.ts` — NEW (R5), full contents

```ts
import { readFileSync } from 'node:fs';
import { dirname, join } from 'node:path';
import { fileURLToPath } from 'node:url';
import { PACKAGE_NAME } from './package.js';

/**
 * The directory holding this package's own manifest, found by walking up from a module's location until a
 * package.json whose `name` is this package appears. Layout-independent on purpose: the same call answers
 * correctly from src/lib/ (a checkout), from dist/lib/ (today's built tree), and from a bundled dist/index.js,
 * which is why every path this package resolves relative to itself goes through here (W-02 / R5). Returns null
 * when no such manifest exists above the caller — every caller treats that as "not running from a package".
 */
const cache = new Map<string, string | null>();

export function packageRoot(from: string = fileURLToPath(import.meta.url)): string | null {
  const cached = cache.get(from);
  if (cached !== undefined) return cached;
  let directory = dirname(from);
  for (;;) {
    let name: unknown;
    try { name = (JSON.parse(readFileSync(join(directory, 'package.json'), 'utf8')) as { name?: unknown }).name; }
    catch { name = undefined; }
    if (name === PACKAGE_NAME) { cache.set(from, directory); return directory; }
    const parent = dirname(directory);
    if (parent === directory) { cache.set(from, null); return null; }
    directory = parent;
  }
}
```

Failure modes handled explicitly: a missing `package.json` (ENOENT), an unreadable one (EACCES), and one that is
not valid JSON all fall through to the parent without throwing; the walk terminates at the filesystem root on
every platform because `dirname` is idempotent there (`/` on POSIX, `C:\` and `\\server\share\` on Windows);
`from` is memoised so the walk runs once per process per caller layout.

`PACKAGE_NAME` is imported from `src/lib/package.ts:3` rather than re-spelled, so there is one literal.

### 4.18 `desktop/src/backend/tauri/concurrency.ts` — NEW (R1 / contract C4), full contents

```ts
/**
 * Bounded-concurrency map for seam reads (W-02). The Rust bridge admits at most 8 children
 * (src-tauri/src/lib.rs) and refuses the 9th, so the callers are bounded rather than the cap raised.
 * Results come back in INPUT order and the reported failure is the LOWEST-INDEXED one, so a fail-fast
 * caller's error text stays the same on a machine whose spawn ordering is noisier.
 */
export const BRIDGE_BUSY = 'too many pending terum-skills processes';

export async function mapWithConcurrency<T, R>(items: readonly T[], limit: number, fn: (item: T, index: number) => Promise<R>): Promise<R[]> {
  const width = Number.isFinite(limit) ? Math.max(1, Math.floor(limit)) : 1;
  const results = new Array<R>(items.length);
  const failures = new Map<number, unknown>();
  let next = 0;
  const worker = async (): Promise<void> => {
    for (;;) {
      if (failures.size > 0) return;
      const index = next++;
      if (index >= items.length) return;
      try { results[index] = await fn(items[index]!, index); }
      catch (error) { failures.set(index, error); return; }
    }
  };
  await Promise.all(Array.from({ length: Math.min(width, items.length) }, worker));
  if (failures.size > 0) throw failures.get(Math.min(...failures.keys()));
  return results;
}
```

The bridge-busy retry lives in the **caller** (`catalog()`), not in the helper, so the helper stays a pure
scheduling primitive with one behaviour. `BRIDGE_BUSY` is exported here because the message the caller must
match arrives **wrapped** (`Could not start terum-skills: too many pending terum-skills processes (8); wait for
one to finish`, produced at `desktop/src/backend/tauri/run.ts:171`) — match the substring, never the whole
string.
