## 0. Summary

1. `eval` (and every other person-initiated verb) dies after ~3.75 s when another process on the same
   machine holds the per-clone writer lock — a lock a legitimate holder keeps for up to ~45 s, and a
   hard-killed holder squats on for 30–60 s. The desktop dialog then shows the raw sentence and one
   **Close** button, so a 25-minute eval is lost with no way to retry.
2. This batch gives a lock contender a real wait budget (75 s when a person is watching, today's 4 s
   otherwise), a visible waiting line while it waits, and an immediate, actionable refusal for a lock
   that waiting cannot clear.
3. It stops the CLI from terminating *itself* with `process.kill(process.pid, 'SIGTERM')` on cancel —
   on Windows that is `TerminateProcess`, which runs no exit hook, so the lock directory is orphaned.
4. It makes the Tauri shell ask its children to stop before killing them, and sweeps the Windows
   process tree with `taskkill /PID <pid> /T /F` so orphaned `claude.exe` descendants stop spending.
5. It gives the run-eval dialog a **Run eval again** button for a run that produced no evaluation.

Audience: Ajay and Teddy on Windows first, everyone second. Merge position: third, after
`w07-library-header` and `w08-refresh-receipts`.

## 3. Decisions taken

Every fork is closed here. Do not re-open one; if reality contradicts one, implement it as written and
put the contradiction in `openQuestions`.

- **D1 — Two budgets, chosen by `Prompter.interactive`, not by a per-verb list.**
  `LOCK_WAIT_MS = 4_000` (today's ladder, for anything nobody is watching) and
  `INTERACTIVE_LOCK_WAIT_MS = 75_000` (a person is on the other end: a TTY, or a program over frames).
  *Why:* `interactive` is the CLI's own, already-tested answer to "is a person watching" —
  `frameChannel` hard-codes `interactive: true` (`src/lib/frames.ts:158`) and `terminalPrompter`
  derives it from `input.isTTY` (`src/lib/prompt.ts:70`). One derivation, one consumer, no list of
  verbs to keep in sync (`CLAUDE.md`: one active path per behaviour). It also gives `sync --hook` the
  short budget **by construction** rather than by a special case. 75 s outwaits the measured 58.9 s
  orphan and the ~45 s legitimate hold with slack; a scripted, non-TTY run of a person-initiated verb
  keeps today's 4 s, which is right — nobody is there to read a waiting line, and a script wants to
  fail fast. *This is a deliberate refinement of the batch brief's "every person-initiated verb"
  wording; the verbs the brief lists are exactly the verbs that reach this code with an interactive
  Prompter.*
- **D2 — Keep `stale: 60_000` exactly as it is.** Shortening it to 15 s would cut orphan recovery from
  58.9 s to 14.5 s and is **rejected**: `proper-lockfile` applies the **contender's** `stale` to the
  **holder's** lock (`lockfile.js:56-81` + `:84-86`), so a new CLI with a 15 s window would judge a
  live 0.1.10 holder (which refreshes every 30 s) stale and steal its lock, leaving two processes
  `git reset --hard`-ing one working tree. Mixed versions are the normal state during a rollout (the
  app spawns a pinned CLI while `npx …@latest` and the session hook resolve independently). Data loss
  beats latency.
- **D3 — Do not break a lock whose pid is dead.** `src/lib/hook.ts:211-212, 221-233, 276` already has
  a pid-liveness reclaim for the *team session* lock, so the precedent exists — but adding a
  lock-breaking race to the one lock that guards `git reset --hard`, on an OS that recycles pids, buys
  nothing that D1's budget does not already buy. Out of scope; recorded in §10.
- **D4 — Do the waiting ourselves (`retries: 0` plus an explicit poll), not with a longer
  `proper-lockfile` ladder.** Only an explicit loop can report progress, and `retries: 0` provably
  still reclaims a stale lock (measured above, 3 ms). Poll every 250 ms + up to 150 ms of full jitter
  so two waiters that arrived together stop colliding on the same tick.
- **D5 — Say only what is measured.** The waiting line carries the label and the elapsed seconds and
  nothing else. It does **not** say a process "was killed" or "is stuck": a lock whose mtime has not
  moved for 35 s is produced identically by a dead holder and by a live holder whose event loop is
  blocked, so naming a cause would be an invented fact — the exact failure mode two fixes on `main`
  already corrected (`faab57b` "marketplace error board stops asserting an invented cause",
  `ff1ff0a` "skill detail stops blaming your people file"). Teddy, 2026-09-09.
- **D6 — The give-up sentence does not change.** `Another terum-skills operation holds the write lock
  on <label>; retry when it finishes.` stays byte-identical, so
  `src/lib/__tests__/teamRepo.test.ts:407-410` and every shell that matches on it keep working. What
  changes is *when* it arrives.
- **D7 — `sync --hook` is gated on `args.hook`, not only on `interactive`.** Its stdout is Claude
  Code's reload directive (`src/commands/sync.ts:431`), and one stray line makes that unparseable
  JSON. `interactive` would already be false in production, but a hook run from a TTY must not be able
  to break the contract, so hook mode gets the short budget and **no** `onWaiting` callback,
  explicitly. (Frame-protocol rule 2, `docs/frame-protocol.md:35`, exists for the same reason.)
- **D8 — A lock stamped in this machine's future fails immediately, with the directory named.**
  `isLockStale` is `stat.mtime.getTime() < Date.now() - options.stale`, so a lock whose mtime is ahead
  of the clock is **never** stale (measured: ELOCKED in 2 ms, forever). Waiting 75 s for it is
  pointless, and the user's only remedy is deleting the directory, which nothing tells them. So: one
  `stat` after the first refusal; if the mtime is more than `LOCK_FUTURE_SKEW_MS = 60_000` ahead,
  refuse at once with a sentence that names the path. Same skew tolerance, for the same reason, that
  the sync stamp already uses (`src/lib/hook.ts:151`, used at `:172`). It stays a `CloneBusy`, so every
  caller's control flow (sync skips the team; publish fails) is unchanged.

```ts
/** How long a caller waits for another process's clone lock before failing: today's ladder, for anything nobody is watching. */
export const LOCK_WAIT_MS = 4_000;
/**
 * A person is on the other end (a TTY, or a program over frames): outwait any legitimate holder — a
 * safeWrite holds this lock across its whole 30-second deadline loop — and any lock a hard-killed
 * holder left behind, which proper-lockfile clears only after its 60-second stale window.
 */
export const INTERACTIVE_LOCK_WAIT_MS = 75_000;
/** Poll cadence while waiting, plus full jitter, so two waiters that arrived together stop colliding on the same tick. */
const WAIT_POLL_MS = 250;
const WAIT_POLL_JITTER_MS = 150;
/** Nothing is said for the first second: a lock that frees within a poll or two is not worth a line. */
const WAIT_NOTICE_AFTER_MS = 1_000;
/** Then at most one line every five seconds, so a 75-second wait is a handful of lines, not seventy-five. */
const WAIT_NOTICE_INTERVAL_MS = 5_000;
/**
 * Staleness is a bare mtime compare against the wall clock (node_modules/proper-lockfile/lib/lockfile.js:84-86),
 * so a lock stamped further than this into this machine's future never goes stale and no wait can clear it: a
 * clock that jumped back, or a store on a mount with a clock of its own. Same tolerance, for the same reason,
 * as the sync stamp's (lib/hook.ts:151).
 */
const LOCK_FUTURE_SKEW_MS = 60_000;

/** What a caller may say about waiting for the clone lock. Accepted by refreshClone, withCloneLock and safeWrite alike. */
export interface LockWaitOptions {
  /** Milliseconds to wait for the lock before failing. Default: LOCK_WAIT_MS. */
  lockWaitMs?: number;
  /** Called while waiting: after the first second, then at most every five. The caller turns it into one printed line. */
  onWaiting?: (info: { label: string; elapsedMs: number }) => void;
  /** Test knobs for the wait loop only (the same convention SafeWriteOptions uses for its push loop). */
  now?: () => number;
  sleep?: (milliseconds: number) => Promise<void>;
}

/** Cross-batch contract C1: refreshClone's one optional trailing options bag. `deadlineMs` is owned by w08-refresh-receipts; this batch accepts and ignores it. */

/**
 * The one lock-wait policy. A person on the other end (a TTY, or a shell over frames) outwaits the
 * holder and is told that it is waiting; anything else — the session hook, a piped script — keeps the
 * short budget and stays silent, because there is nobody to read the line and a script wants to fail fast.
 */

  return { lockWaitMs: waitMs ?? INTERACTIVE_LOCK_WAIT_MS, onWaiting: (info) => io.print(waitingLine(info)) };
}
```

```ts
async function acquireCloneLock(root: string, options: { lockStale?: number; label?: string; onCompromised: () => void } & LockWaitOptions): Promise<() => Promise<void>> {
  const now = options.now ?? Date.now;
  const sleep = options.sleep ?? wait;
  const started = now();
  const deadline = started + (options.lockWaitMs ?? LOCK_WAIT_MS);
  let announced: number | undefined;
  let stamped = false;
  for (;;) {
    try {
      return await lockfile.lock(root, { lockfilePath: cloneLockPath(root), realpath: false, stale: options.lockStale ?? 60_000, retries: 0, onCompromised: options.onCompromised });
    } catch (error) {
      // Only contention waits. EACCES on the store, ENOTDIR from a path that is not a directory, a
      // read-only volume: each is what it says it is, and is raised on the first attempt exactly as before.
      if ((error as NodeJS.ErrnoException).code !== 'ELOCKED') throw error;
      if (!stamped) { stamped = true; await refuseUnusableLock(root, options.label, now); }
      const elapsed = now() - started;
      if (now() >= deadline) throw new CloneBusy(`Another terum-skills operation holds the write lock on ${options.label ?? root}; retry when it finishes.`);
      if (options.onWaiting && elapsed >= WAIT_NOTICE_AFTER_MS && (announced === undefined || elapsed - announced >= WAIT_NOTICE_INTERVAL_MS)) {
        announced = elapsed;
        options.onWaiting({ label: options.label ?? root, elapsedMs: elapsed });
      }
      await sleep(WAIT_POLL_MS + Math.floor(Math.random() * WAIT_POLL_JITTER_MS));
    }
  }
}

/**
 * A lock whose mtime is in this machine's future is not held, it is unusable: proper-lockfile will
 * never call it stale, so waiting cannot clear it and the only remedy is removing the directory. Say
 * that, once, instead of spending the whole budget on it. Everything in the sentence is measured.
 */
async function refuseUnusableLock(root: string, label: string | undefined, now: () => number): Promise<void> {
  const lockPath = cloneLockPath(root);
  let aheadMs: number;
  // A lock that vanished between the refusal and this stat, or one this process cannot stat, is not
  // evidence of anything: fall through and let the ordinary wait decide. Continuing is safe because
  // the very next acquisition attempt re-tests the real condition.
  try { aheadMs = (await stat(lockPath)).mtimeMs - now(); } catch { return; }
  if (aheadMs <= LOCK_FUTURE_SKEW_MS) return;
  throw new CloneBusy(`The write lock on ${label ?? root} is stamped ${Math.round(aheadMs / 1000)} s in this machine's future (${lockPath}), so waiting cannot clear it; remove that directory if no terum-skills command is running.`);
}
```

```ts
/**
 * One shutdown path for the whole bin. A cancel (docs/frame-protocol.md's `cancel` frame) and a POSIX
 * SIGTERM both mean the same thing — stop now, but clean up first — and both must reach the same code,
 * because on Windows there is no signal at all: terminating the process runs nothing.
 *
 * Hooks are synchronous and best effort. They are what kills tracked child processes; releasing file
 * locks is NOT their job — `process.exit` in src/index.ts emits 'exit', which is what signal-exit and
 * proper-lockfile hang their own cleanup off (verified: a held clone lock is removed by process.exit
 * on this platform). This module deliberately does not reference `process`: eslint.config.js:24 gives
 * src/index.ts sole ownership of the exit, and keeping it out of here means no rule exception and a
 * unit test that needs no process.
 */
const hooks = new Set<() => void>();

/** Register work that must happen before the bin exits. Registration order is run order. */
export function onShutdown(hook: () => void): void { hooks.add(hook); }

/** Run every registered hook exactly once, in registration order. Never throws. */
export function runShutdownHooks(): void {
  for (const hook of [...hooks]) {
    hooks.delete(hook);
    // A hook that throws must not take the remaining hooks — or the exit — down with it: this is the
    // last code that runs, there is no channel left to report on, and the next line is process.exit.
    try { hook(); } catch { /* see above */ }
  }
}
```

```rust
/// The descendant-kill argv for a Windows child tree. Split out from the spawn so it is unit-testable on any host.
#[cfg_attr(not(any(windows, test)), allow(dead_code))] // the Windows kill path and the test below are its only callers
fn taskkill_args(pid: u32) -> [String; 4] {
  ["/PID".to_string(), pid.to_string(), "/T".to_string(), "/F".to_string()]

/// Windows has no process group to signal: `Child::kill` is TerminateProcess on the direct child alone,
/// so an eval's `claude.exe` grandchildren outlive it and keep spending the user's account. `taskkill /T`
/// walks the tree. Run before `Child::kill`, while the tree is still rooted at a live pid; the open Child
/// handle keeps that pid reserved, so this can never reach an unrelated process. A missing or refusing
/// taskkill.exe is not fatal — the `Child::kill` that follows is exactly today's behaviour, and there is
/// no channel here to report on.
#[cfg(windows)]
fn kill_tree(pid: u32) {
  let _ = Command::new("taskkill")
    .args(taskkill_args(pid))
    .creation_flags(CREATE_NO_WINDOW)
    .stdin(Stdio::null())
    .stdout(Stdio::null())
    .stderr(Stdio::null())
    .status();
}
```

**(d) `kill_all` (`:191-217`)** becomes:

```rust
/// Stop all admitted children while holding admission closed. Unix descendants share the group.
/// Every child is asked to stop through the protocol first: a terminated CLI runs no cleanup, so on
/// Windows a write in flight would leave the clone's writer lock directory behind for up to a minute.
/// Closing stdin is not a substitute — src/lib/frames.ts fails pending questions on end-of-input and
/// never calls the cancellation hook, so a verb that asks nothing (eval) would keep running.
fn kill_all(bridge: &Bridge) {
  if let Ok(mut children) = bridge.children.lock() {
    if children.is_empty() { return; }
    for handle in children.values() {
      if let Ok(mut guard) = handle.lock() {
        if let Some(stdin) = guard.stdin.as_mut() {
          // Best effort: a child whose pipe is already gone is a child that is already stopping.
          let _ = stdin.write_all(b"{\"t\":\"cancel\"}\n").and_then(|_| stdin.flush());
        }
        guard.stdin.take();
      }
    }
    std::thread::sleep(Duration::from_millis(CANCEL_GRACE_MS));
    #[cfg(unix)]
    {
      for handle in children.values() {
        if let Ok(guard) = handle.lock() {
          // SAFETY: cli_spawn created this child's process group; negative pid addresses that group.
          unsafe { libc::kill(-(guard.child.id() as i32), libc::SIGTERM); }
        }
      }
      std::thread::sleep(Duration::from_millis(300));
      for handle in children.values() {
        if let Ok(guard) = handle.lock() {
          // SAFETY: escalate the same group even when its leader has already exited.
          unsafe { libc::kill(-(guard.child.id() as i32), libc::SIGKILL); }
        }
      }
    }
    #[cfg(windows)]
    for handle in children.values() {
      if let Ok(mut guard) = handle.lock() {
        // Descendants outlive the leader here, so sweep the tree even if the leader is already gone;
        // the open Child handle keeps its pid reserved, so the sweep cannot hit an unrelated process.
        kill_tree(guard.child.id());
        let _ = guard.child.kill();
      }
    }
    children.clear();
  }
}
```

Only the cancel phase, the sleep and the Windows branch are new; the two `#[cfg(unix)]` loops keep

## 12. PR

**Title** (conventional, 61 chars): `fix(cli): wait out the clone lock and release it on cancel`

**Body outline**

- **What.** A person-initiated verb now waits up to 75 s for another process's clone writer lock,

## 13. Open questions (each with the default you MUST take without asking)

1. **A wedged holder still ends in a 75-second failure.** No git call under the writer lock has a
   deadline (`src/lib/teamRepo.ts:91`, `:480`), so a `fetch` parked on a dead remote or an unanswered
   Windows credential helper holds the lock forever while `proper-lockfile` keeps refreshing its mtime.
   **Default: implement nothing here.** Contract C1 gives `RefreshOptions.deadlineMs` to
   `w08-refresh-receipts`; a second implementation of the same field is a guaranteed conflict. Follow-up
   for the orchestrator: a generous fetch deadline (~120 s) and a short one for `reset`/`ls-files`/`commit`,
   whose failure reads as "could not reach the remote" through `explainGitAccessFailure`, never as a
   lock error. Note `grouped` is false on Windows (`src/lib/runner.ts:36`), so a deadline there kills
   `git.exe` but not a transport grandchild — enough to release the lock, not enough to be silent about.
2. **Re-entrancy.** `proper-lockfile` has no re-entrancy registry: a second acquisition of the same
   clone **inside one process** is ELOCKED. No path in `src/` nests today (`refreshClone` is never
   called under `withCloneLock`/`safeWrite`), but after this change a future nesting would be a silent
   75-second self-deadlock instead of a fast 3.75-second error. **Default: do not add a
   process-local held-set now** (it is new state on the one lock that guards `git reset --hard`, for a
   case that does not exist). Recorded so the next person who nests one knows what they will see.
3. **The commit checkbox is disabled on a retry** (`RunEvalDialog.tsx:34`, `disabled={active!==null}`),
   so a user who wants to retry *with* a different commit choice must close the dialog and reopen it.
   **Default: leave it disabled** and send the displayed value (D16). Re-enabling it is a design fork
   for Teddy, not an implementation choice.
4. **`sync` waits per team.** The budget is per clone, so a machine with N busy teams could wait up to
   N × 75 s before skipping them all. One team per machine is the ruling, so N is 1 in practice.
   **Default: keep one constant, applied per team.**
5. **The bridge's 8-child cap** (`desktop/src-tauri/src/lib.rs:66`) now sees a mutating verb occupy a
   slot for up to 75 s longer. Against an eval that already holds a slot for 25 minutes this is
   marginal. **Default: leave the cap at 8.**
6. **Is `--setting-sources project` (`src/lib/evals/agent.ts:192`) permanent?** It is the only thing
   stopping every eval agent from firing `sync --hook` and colliding with the very lock the run holds.
   **Default: keep it, and keep the comment 4.6 adds.** A test that pins the argv needs a real spawn,
   so it is not added here; the comment is the guard.
