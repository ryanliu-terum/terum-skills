## 0. Summary

1. The desktop app can see that a newer release exists and does nothing about it: the "The app" row on Settings ▸ Updates is a hard-coded sentence, and no updater exists anywhere in the product.
2. This batch adds a CLI verb `app-update` with three modes (`--check`, `--stage`, `--apply`) plus one hidden detached mode (`--apply-now`), so the CLI — which already downloads and checksums desktop builds for `terum-skills app` — can fetch **any** published version and hand the install to a process that outlives the app.
3. The app gains a seam member `Backend.appUpdate`, a `Surfaces.appUpdate` flag, a `FEATURE_KEYS` entry `appUpdate`, real rows on Settings ▸ Updates, an auto-download preference, and one check per app launch (never a timer, never on focus).
4. There is **no Rust change**, **no release-workflow change**, **no Tauri updater plugin**, and **no minisign key**: Windows reuses the NSIS installer's own `/S /UPDATE /R` (the same argument set the official Tauri updater uses), macOS reuses the per-version bundle directories `terum-skills app` already writes.
5. For whom: Teddy on Windows x64 (the reporter), and every user whose app is older than the advertised release. Why now: 0.1.10 shipped and the app tells the user, on one screen, that 0.1.10 exists, that it is 0.1.9, and that it will do nothing.

## 3. Decisions taken — every fork closed

**DECISION D1 — the option is `--release <version>`, never `--version <version>`.**
`src/cli.ts:44` registers `program.version(packageVersion() ?? 'version unknown', '-v, --version');`. With the pinned commander that program-level option wins **inside subcommand parsing**: a subcommand option literally named `--version` never reaches the action handler. Reproduced on the built bin at this repo: `node dist/index.js --frames status --version </dev/null` emits the hello frame, writes the bare line `0.1.10` onto the frame channel (stdout), and exits 0 **with no `result` frame**, because `src/index.ts:83` classifies `commander.version` at exit code 0 as a `COMMANDER_NON_ERRORS` non-error (`src/lib/frames.ts:46`) and never calls `report()`. The desktop seam then surfaces `terum-skills exited with code 0 before reporting a result. unparseable line from terum-skills: 0.1.10`. Worse, the detached `--apply-now` leg carries no `--frames` and no reader: it would print `0.1.10`, exit 0, install nothing and write no marker, while the app had already quit on a successful `--apply`. **Use `--release <version>` everywhere** — the verb, the adapter argv, the hidden leg, the tests. Do **not** reach for `program.enablePositionalOptions()`: it changes option parsing for all 26 registered verbs to buy a flag name.

**DECISION D2 — one test must drive the new verb through `buildProgram(...).parseAsync([...])`.** Unit tests that call `run(args, io)` directly cannot see D1's failure class; the shipped verb would no-op while every unit test passed. §7 names that test.

**DECISION D3 — do not touch `src/lib/runner.ts`.** The triage proposed adding `RunOptions.windowsHide` and passing `true` in the detach branch "because `detached: true` on Windows gives the child its own console". That justification is false: libuv's `src/win/process.c` sets `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` for `UV_PROCESS_DETACHED`, and Microsoft's *Process Creation Flags* documentation states `CREATE_NO_WINDOW` "is ignored if the application is not a console application, or if it is used with either CREATE_NEW_CONSOLE or DETACHED_PROCESS", while `DETACHED_PROCESS` means "the new process does not inherit its parent's console". `detached: true` already implies no console. Adding the option would be a no-op with a false comment. `src/lib/runner.ts` is therefore **out of scope** (§10).

**DECISION D4 — the capability split rides `Surfaces` + `Features`, not a new `Capabilities` key.**
The batch brief proposed `Capabilities.appUpdates: 'none'|'notice'|'full'`. Take the two mechanisms that already exist instead:
- `Surfaces.appUpdate: boolean` — "the real adapter declares which read models it serves" (`desktop/GAPS.md:3`). Mock `false`, real adapter `true`. The precedent is one section above the target line in the same file, `desktop/src/screens/settings/SettingsContent.tsx:78`: `{features?.checkouts && surfaces?.checkouts === true ? <Group label="Checkouts" …> : null}`, with `mock.surfaces().checkouts === false` (`desktop/src/backend/mock/index.ts:107`) and `tauri.surfaces().checkouts: true` (`desktop/src/backend/tauri/index.ts:507`).
- `FEATURE_KEYS`/`hello.features.appUpdate` — does the *driving CLI* have the verb (`desktop/AGENTS.md` invariant 2; a missing key reads `false` at `desktop/src/backend/tauri/index.ts:500`).

The rendered mode is derived in the screen: `surfaces?.appUpdate !== true ? 'none' : features?.appUpdate ? 'full' : 'notice'`.
Why: it leaves `Capabilities` untouched, so the exhaustive assertion at `desktop/src/backend/tauri/__tests__/run.test.ts:259` (`expect(await backend.capabilities()).toEqual({ appVersion: …, windowChrome: 'mac-overlay', disablePerMachine: false, inboxEventLog: false, offtargetKind: false, machineRegistry: false, perCaseEvalTables: false, evalCommitChoice: false, openInEditor: true, clipboard: true })`) stays green untouched, and only one existing assertion changes. It also avoids a new `GAPS.md` capability ruling, which is maintainer-owned (`desktop/AGENTS.md` invariant 2) and which you may not write.
*(Correction to a claim you may see elsewhere: adding a string-union capability would **not** be "the first non-boolean capability" — `desktop/src/backend/types.ts:11` already has `windowChrome:'mac-overlay'|'native'|'cosmetic'`. The reason to prefer Surfaces is the untouched `toEqual` and the maintainer-owned GAPS entry, not the type shape.)*

**DECISION D5 — `--check` never probes the network by default; `--check --force` probes exactly as `update` already does.**
`src/lib/update.ts:140-155` `maintainReleaseState` writes `state.attempt.at` on every probe, and both the CLI's interactive-sync probe and its stderr notice are gated on `fresh(state?.attempt?.at, now)` (`src/lib/update.ts:147`, `src/index.ts:55`). A launch-time probe from the app would silently consume the CLI's daily budget. So:
- `app-update --check` with no `--force`: **zero network, zero writes.** It reads `~/.terum/skills/run/latest-version.json` through `createReleaseState(store.root).read()` and `describeUpdate(...)` (both already exported from `src/lib/update.ts:36` and `:159`), plus `probePolicy(await store.read())` (`src/lib/update.ts:88`) to distinguish `'skipped'` from `'cached'`, plus the `~/.terum/skills/app/*/` directories.
- `app-update --check --force`: calls `maintainReleaseState({ …, probe: probePolicy(await store.read()), force: true })` — byte-for-byte the same policy and the same command `update` already runs at `src/commands/update.ts:21`. Nothing new is granted, so the locked board sentence at `desktop/src/screens/settings/SettingsContent.tsx:86` ("Reads release tags from github.com/ryanliu-terum/terum-skills … only while a team on this machine lives on GitHub") stays true.
Consequence, accepted deliberately: a machine with no GitHub-hosted team has `probePolicy → 'nobody'` and never learns about releases; the row says so honestly (§5). Widening that predicate is a product decision, not yours.
Implementation note that is easy to get wrong: `maintainReleaseState` returns `null` for **both** `probe === 'nobody'` (`src/lib/update.ts:144`) and the fresh-cache case (`:147`), so the return value alone cannot tell `'skipped'` from `'cached'`. Compute `probe` from `probePolicy(...)` and `state.attempt` yourself.

**DECISION D6 — three UI modes; the mock is pinned to `'none'` so the locked board never moves.**

6. Return `success({ mode: 'apply', version, platform, awaitPid, handedOff: true })` immediately. **This verb never kills the app; the shell quits itself.**

**`--apply-now`** (hidden; detached; nothing is reading its output). It writes `~/.terum/skills/run/app-update.json` through `writeJsonPrivate` at every phase so the relaunched app can report what happened:
1. `{ schema:1, version, phase:'waiting', at, error:null }`. If `awaitPid !== null`, poll `alive(pid)` — default `() => { try { process.kill(pid, 0); return true; } catch (error) { return (error as NodeJS.ErrnoException).code === 'EPERM'; } }` (an `EPERM` means the process exists and is not ours) — every `args.pollMs ?? 100` ms up to `args.waitMs ?? 30_000`.
   - Exited → continue.
   - Timed out on **Windows** → continue anyway (the installer's own `CheckIfAppIsRunning` kills a survivor under `/S`).
   - Timed out on **macOS** → write `phase:'failed'`, `error: 'The desktop app was still running after 30 seconds, so the new version was not opened.'`, and return `success({ mode:'apply-now', version, platform, phase:'failed', error })` **without calling `open`** — an `open` now would only re-activate the old instance.
2. `phase:'installing'`.
3. **Windows**: `const outcome = await exec(join(appRoot, version, installer), ['/S', '/UPDATE', '/R']);` awaited.
   - `/S` silent, `/UPDATE` (skips the WebView2 bootstrapper and desktop-shortcut re-creation), `/R` (relaunches the installed exe as the logged-in user). These three flags are present verbatim in the string table of the shipped `terum-skills-desktop_0.1.10_x64-setup.exe` asset alongside `FindProcessCurrentUser`, `KillProcessCurrentUser`, `RunAsUser` and `"$INSTDIR\terum-skills-desktop.exe"`; they are the same argument set the official Tauri updater passes.
   - exit 0 → write `installed.json` in the version directory (`{ schema:1, version, platform, bundle:null, installedAt }`), `phase:'launched'`, and **do not launch anything** — `/R` already did, and there is no single-instance plugin, so a second launch means two windows.
   - exit ≠ 0 → `phase:'failed'` with `` `The desktop app installer exited with code ${outcome.code}. ${(outcome.stderr || outcome.stdout).trim()}`.trim() ``, then the fallback: `const existing = await locateApp(platform, join(appRoot, version), args.localAppData); if (existing) await exec(existing, [], { detach: true });` — exactly once, so the user is never left with no app.
4. **macOS**: `await exec('open', [join(appRoot, version, bundle)])` — **no `-n`**. exit 0 → `installed.json`, `phase:'launched'`; non-zero → `phase:'failed'` with the exec's own text.
5. **Never write `app.json`** (D7).
6. Prune, only after a `phase:'launched'`: list `appRoot` entries matching `/^\d+\.\d+\.\d+$/`, sort descending with `compare`, and `rm` every directory that is *not* one of: the two newest, the version just launched, or `packageVersion()`. Never touch a `.download-*` directory here (step 4 of `--stage` owns those) and never touch an entry whose name does not match the version pattern. Every `rm` is individually `.catch(() => undefined)`: a failed prune must not turn a successful update into a failure.
7. Return `success({ mode:'apply-now', version, platform, phase, error })`.

### 4.12 `desktop/src/lib/version-compare.ts` — NEW (full contents)

```ts
/** Stable-channel comparison, the same three-segment rule the CLI uses (src/lib/update.ts:78).
 *  Anything that is not exactly x.y.z (the mock's "0.1.0 (build 12)", a prerelease tag, null)
 *  is not comparable, and an incomparable pair is never "newer". */
export function isNewer(candidate: string | null | undefined, running: string | null | undefined): boolean {
  if (!candidate || !running || !/^\d+\.\d+\.\d+$/.test(candidate) || !/^\d+\.\d+\.\d+$/.test(running)) return false;
  const left = candidate.split('.').map(Number), right = running.split('.').map(Number);
  for (let i = 0; i < 3; i++) { if (left[i]! > right[i]!) return true; if (left[i]! < right[i]!) return false; }
  return false;
}
```

### 4.18 `desktop/src/app/useAppUpdateCheck.ts` — NEW (full contents)

```tsx
import { useEffect } from 'react';
import { useQueryClient } from '@tanstack/react-query';
import { useBackend } from '../backend';

/** One check per app process (m7 decision walk row 9: no timer, no poll, and — deliberately narrower
 *  than that gate — not on window focus either, because a check can reach the network). When the
 *  preference allows it and a newer app is advertised, the download starts here and the Relaunch
 *  button on Settings ▸ Updates is what installs it. Every failure is swallowed: a launch must never
 *  be worse because an update check did not work. */
export function useAppUpdateCheck(): void {
  const backend = useBackend(), client = useQueryClient();
  useEffect(() => {
    let disposed = false;
    void (async () => {
      try {
        const surfaces = await backend.surfaces();
        if (disposed || !surfaces.appUpdate) return;
        const features = await backend.features();
        if (disposed || !features.appUpdate) return;
        await backend.prefs.ready;
        const status = await client.ensureQueryData({ queryKey: ['app-update'], queryFn: () => backend.appUpdate.check(), staleTime: Infinity, gcTime: Infinity, retry: false });
        if (disposed || !status.ok) return;
        const latest = status.value.latest;
        if (!status.value.newer || latest === null || status.value.staged === latest) return;
        if (!backend.prefs.get('updates:app:auto', true)) return;
        const staged = await backend.appUpdate.stage(latest).done;
        if (disposed || !staged.ok) return;
        client.setQueryData(['app-update'], { ok: true, value: { ...status.value, staged: staged.value.staged ? latest : status.value.staged } });
      } catch { /* A failed launch-time check leaves Settings ▸ Updates to report it on demand. */ }
    })();
    return () => { disposed = true; };
  }, [backend, client]);
}
```

## 9. Windows verification — what cannot be verified here

The whole Windows install leg is unverifiable on Linux. These are the falsifiers; the reporter runs them on Windows 11 x64.

**9.1 The install-and-relaunch mechanism (hard gate before this ships).**
With app 0.1.11 installed and running, from a Windows terminal:
```
"%LOCALAPPDATA%\Terum Skills\..\terum-skills-desktop_0.1.12_x64-setup.exe" /S /UPDATE /R
```
(or, after `app-update --stage --release 0.1.12`, the staged path `%USERPROFILE%\.terum\skills\app\0.1.12\terum-skills-desktop_0.1.12_x64-setup.exe`.)
Expected: the running window closes, the exe under `%LOCALAPPDATA%\Terum Skills\` is replaced, and the app reopens at 0.1.12 without a UAC prompt. If it does not, this design's Windows leg is wrong and the fallback is the official Tauri updater (which needs an Actions secret only Ryan can provision).

**9.2 Is `process.ppid` inside the CLI the Tauri app on Windows?**
In the app, open Settings ▸ Updates and read the `ppid` that `app-update --check` reports (it is in the result value; surface it in the report or read it from the frame log). Compare with `terum-skills-desktop.exe`'s PID in Task Manager. If they differ, `--await-pid`'s default is watching the wrong process and a seventh Rust command returning the app's PID is required.

**9.3 Is the app inside a Job object?**
libuv does not set `CREATE_BREAKAWAY_FROM_JOB` for a detached child. If `terum-skills-desktop.exe` runs inside a Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, the detached applier dies with the app. Cheap probe: Process Explorer on `terum-skills-desktop.exe` (or `IsProcessInJob`), **or** simply press Relaunch and check whether `%USERPROFILE%\.terum\skills\run\app-update.json` ever appears. If the marker never appears, this is the cause.

**9.4 Does `/R` fire when the installer was started by a console-less detached `node.exe`?**
Watch specifically for: the install lands (the exe is replaced) but the app does not reopen. The non-zero-exit fallback does **not** cover this, because `/R` failing to relaunch still exits 0. If it happens, the applier must launch the exe itself on the success path too, and the "two windows" risk must be handled by a single-instance check.

**9.5 macOS `open` after the PID wait.** Not run here against a real bundle. On a Mac: install 0.1.11, launch it, press Relaunch, confirm the old process exits and a 0.1.12 window appears (not the old one re-activated).

**9.6 UNC / WSL paths.** This batch introduces no path-prefix comparison (no `root + '/'` check, no `startsWith` on a path). Every path it builds goes through `node:path` `join`. `~/.terum/skills` is derived from `homedir()` inside `createConfigStore` exactly as every other verb does. Nothing here needs `path.win32`-aware comparison — say so in your report rather than inventing one.

## 12. PR

**Title** (conventional, 61 characters):
```
feat(app-update): update the desktop app from inside the app
```

**Body outline:**

- **What.** A new CLI verb `app-update` (`--check` / `--stage` / `--apply`, plus a hidden detached `--apply-now`) and a desktop seam member `Backend.appUpdate`. Settings ▸ Updates gains real rows for "The app": the advertised version, a Download button, an auto-download switch, and one **Relaunch now** button that always asks first. The app checks once per launch — no timer, no polling, not on focus.
- **Why.** Bugs.pdf W-01. The app could see that 0.1.10 existed, say it was 0.1.9, and do nothing about it. The row was a string literal and no updater existed anywhere in the product.
- **How, and what it deliberately does not do.** No Rust change (`createUpdaterArtifacts` stays `false`, six commands stay six, no updater or process plugin). No release-workflow change — the release already builds, checksums and gates all eight desktop assets. No minisign key, so no Actions secret. Windows reuses the shipped NSIS installer's own `/S /UPDATE /R` (the same argument set the official Tauri updater passes); macOS reuses the per-version bundle directories `terum-skills app` already writes. The installer runs from a **detached grandchild** of the app, so `kill_all` on window destroy does not take it with the app. The app never updates the CLI; the CLI card keeps its printed command.
- **Consent and network.** `app-update --check` makes **no** network call by default: it reads the release advertisement the CLI already caches. `--check --force` runs exactly the probe `terum-skills update` already runs, under the same team-gated policy, so the drawn Release-probe sentence stays true. A machine with no GitHub-hosted team never probes and the row says so.
- **The bootstrap gap (state this prominently).** 0.1.10 users cannot auto-update to 0.1.11 — there is no update code in 0.1.10. The first hop is manual: `npx -y terum-skills@latest app`. Machines whose CLI predates this verb see the honest read-only *notice* row (`hello.features.appUpdate` absent → `false`).
- **Fidelity.** No board redrawn, no row re-baselined, no mask added. The mock reports `surfaces().appUpdate === false`, so `#/settings/updates` renders byte-identically and `SettingsUpdates` stays `locked` at 0.0030.
- **Windows notes.** The install-and-relaunch path is unverifiable on Linux. Three things must be confirmed on Teddy's box before this is trusted: (1) `/S /UPDATE /R` really replaces and relaunches a running app; (2) `process.ppid` inside the CLI really is the Tauri process on Windows (`--check` reports it); (3) the app is not inside a Job object with kill-on-close, which would take the detached applier down with it. §9 has the exact commands. On macOS, `open` is used without `-n` on purpose, after waiting for the old process to exit.
- **Known limitation.** On macOS only, after an app-only update, `terum-skills app` from the *older* CLI reopens the older per-version bundle; updating the CLI fixes it. Windows has one install path and is unaffected.
- **How verified.** The gate list from §8 with real counts, plus an explicit statement of what could not be run (cargo, `e2e:fidelity`, `export:check`).
