# Eval-gen — dynamic test generation (IE5)

**Status:** rev 2 (Ajay, 2026-09-08; Terum a5ec5efd). Rev 1 SHIPPED as IE5 (merged
PR #36). Rev 2 supersedes rev 1's §3.2 refusal and §4's "no auto-commit under any
flag" for the skill's own author: generated cases live inside the skill folder like
authored cases and may back committed receipts. For an author running
`eval --commit` on an asset-less skill, the command generates, prints the generated
assets, and pauses on one explicit `io.confirm` — on yes it commits them into the
skill via the ordinary sync/reconcile path (a normal hygiene-checked `safeWrite`;
no new write path, no guard change), re-resolves the NEW committed version,
runs the arms there, and lands the receipt; on no, the assets stay in the run tree
and the run continues uncommitted exactly as rev 1. §4.1 pinning is preserved by
construction — the cases enter the tree BEFORE the receipted run. Non-authors are
unchanged (run-tree only, `--commit` refused): only the sharer has a writable
source and guard row a only admits the author's own skill writes. `--save`
(rev 1) remains for the deliberate two-step. This supersedes standing decisions
40dcfb54 (review-then-save-then-rerun) and 6fafb8d3 (run-tree only / eval never
writes the skill); the review pause survives as the in-command confirmation.

DRAFT rev 1 (Ajay, 2026-09-07). Pulls ME5 forward: supersedes the two
2026-09-07 deferral rulings ("ME5 waits for engine mileage" and "authored cases only —

generator, no taxonomy policing beyond schema validation. The safeguard is the same

## 1. Behavior

`terum-skills eval <name>` gains an automatic generation step:

- **Zero eval assets → generate, then run.** After skill resolution, hygiene, and
  preflight, the command inspects the candidate dir. Each asset kind is checked
  independently: no `evals/cases/*.yaml` → generate execution cases; no
  `evals/triggers.yaml` → generate a trigger file. Missing kinds are generated,
  present kinds are used as-is — authored assets always win.
- **Assets exist → skip generation.** Default behavior for any skill with authored
  (or previously saved) assets is byte-identical to today's flow. No agent call, no
  new output.
- **Flags:**
  - `--no-gen` — never generate. A zero-asset run then behaves exactly as today
    (empty report / triggers-null), for scripting and for members who want the old
    semantics.
  - `--gen` — force regeneration of **both** kinds into the run tree even when
    authored assets exist, and evaluate with the *generated* set for this run only.
    Authored files are never read into the run and never touched. (Use case: a
    second opinion on coverage; the report banner names which set ran.)
  - `--save` — valid **only with `--working`**: after validation, also write the
    generated assets into the member's shared source dir
    (`<shared.source>/evals/…`). See §3.
- **`--case <stem>` with zero authored cases keeps today's error** ("No eval case
  named …"). Naming a case asserts an authored expectation; generation does not
  rescue it.
- Generation respects `--triggers-only` / `--execution-only`: only the kind(s) the
  run will actually use are generated.

## 2. The generator (`src/lib/evals/generate.ts`)

New module, same house rules (library-first, `Result<T>`, injected `AgentApi`, no
new deps). It is **pure orchestration over `askJson`** — `agent.ts` remains the only
module that spawns `claude`.

**Inputs** (assembled by `commands/eval.ts`):
- Full `SKILL.md` text of the candidate (frontmatter + body) and the candidate's
  file listing (names only, from `sourceFiles`) — full text deliberately, per the
  accepted-risk ruling above; a blinded generator writes worse cases.
- The endorsed catalog string already built for trigger evals (`endorsedCatalog`) —
  sibling skill names + descriptions are the raw material for **near-miss**
  `should_not_trigger` prompts, which §5.2 requires ("unrelated prompts are
  worthless").
- Counts (defaults, overridable later if needed — not flags in rev 1): 5
  `should_trigger`, 5 `should_not_trigger`, 3 execution cases of which ≥1 carries
  `bucket: adversarial`.
- `model` — the run's `--model`; generation cost rides the member's subscription.

**Output contract** — one `askJson` call per kind, validated hard before use:
- Triggers must round-trip through the existing `parseTriggers`.
- Each case must round-trip through the existing `loadCase` **and** satisfy the
  generation-only whitelist:
  - `checks` kinds limited to `transcript_mentions`, `command_matching`,
    `no_command_matching`, `file_exists`, `file_absent`. **`command_succeeds` is
    excluded**: it makes the generator author a verification *program*, and a wrong
    verifier silently corrupts scores in both arms; the other five kinds are
    declarative and inspectable at a glance. (Veto cheap — lifting the exclusion is
    a one-line whitelist edit.)
  - No `fixture` field (there is no fixture tree to reference); sandbox seeding is
    inline `files` and `setup` only.
  - `bucket` required on every generated case, from the §5.1 taxonomy.
  - `task` must obey the §5.1 authoring rule (headlessly answerable, no
    magic-string incantations) — stated in the generation prompt; not statically
    checkable.
- Validation failure → re-ask with the validator's error appended, **2 retries per
  kind**, then the run **fails** with the last validation error and a hint to retry
  or pass `--no-gen`. A member who ran `eval` on a bare skill wants coverage, not a
  silently empty report.

**File form:** generated assets are written as ordinary YAML files, each opening
with the header comment
`# generated by terum-skills eval-gen — review before trusting` plus a provenance
line (`# model: <m> · engine: <version> · <UTC timestamp>`). YAML comments survive
`loadCase`/`parseTriggers` untouched, and the header travels with the file if a
member later copies it anywhere by hand.

## 3. Where generated assets live — and the receipt rule

This is the load-bearing design decision. Two frozen contracts collide with naive
"just write into the skill folder":

- **§6.0:** `eval` writes only its run tree and (with `--commit`) one receipt. It
  never touches `skills/**` — not in the team clone, not in the store.
- **§4.1:** the tree hash is the dataset digest. A receipt is only meaningful if the
  cases that produced it are pinned inside the version it names.

**Resolution:**

1. **Generated assets are written to the run tree**, not the skill:
   `<runDir>/generated/cases/*.yaml`, `<runDir>/generated/triggers.yaml`. The run
   loads cases/triggers from there (the `casesDir`/trigger path swap in
   `commands/eval.ts` is the entire integration point; `runCase` and
   `runTriggerEvals` are unchanged). §6.0 stays intact verbatim.
2. **A run that used any generated asset refuses `--commit`** — *rev 2: for
   non-authors only.* The receipt would name a tree hash that does not contain the
   cases that judged it. Error text points at the path to a committable receipt
   (step 4). **Rev 2 author path:** when the member IS the skill's sharer
   (`config.shared[id]` exists), `--commit` instead prints the generated assets and
   asks one `io.confirm` question naming the skill; on yes: save into the shared
   source, commit via the ordinary sync/reconcile path, re-resolve the new version,
   re-materialize, run the arms at the committed version, land the receipt (which
   now pins the cases — §4.1 intact by construction). On no, or on a
   non-interactive prompter: continue as a normal generated run, no commit, run
   tree only. Generation happens ONCE; the saved files are byte-identical to the
   confirmed ones, headers included.
3. The report banner states what ran: `cases: generated (3) · triggers: generated`
   vs `authored`, and prints the generated-asset path with the review instruction.
4. **The path to a real receipt** is review-then-commit: the member copies the
   reviewed files into their skill source's `evals/` (or uses `--working --save`,
   which writes them there directly), publishes/shares as normal so the assets ride
   the tree hash, and re-runs `eval --commit` at the committed version. From that
   moment they are ordinary authored-equivalent assets: pinned, receipted,
   publish-gate-eligible, and generation skips them forever after.

`--save` is the single new write path and it targets only the member's **own
working source dir** (`config.shared[id].source` — the same dir `--working` reads),
never the store clone, never a placed skill, never the team repo. It is flag-gated,
never automatic, and refuses to overwrite: if `<source>/evals/` already contains a
`cases/` dir or `triggers.yaml` for a kind being saved, that kind errors instead of
clobbering (authored work is never overwritten by a generator).

**Consequence for the IE4 publish gate — intended, not incidental:** a case-less
skill cannot mint a publish-worthy receipt from thin air mid-eval. The generator
gets it a *reviewed* dataset in two short steps, and only committed, human-reviewed
cases ever back a publish PR. CI remains deterministic and key-free; it never sees,
runs, or validates generation.

**Run-tree provenance:** the run meta line gains an additive optional field
`generated_assets: { cases: boolean, triggers: boolean }` so later tooling can tell
these runs apart. The frozen `receiptSchema` is untouched — runs with generated
assets never produce receipts (point 2), so no receipt field is needed.

## 4. What this spec deliberately does not do

- **No anti-circularity machinery** (generator blinding, held-out authoring,
  cross-model generation). Accepted risk, Ajay 2026-09-07. Revisit only if reviewed
  generated cases prove systematically self-congratulatory in practice.
- **No CI involvement** — generation is a local, subscription-funded, member-run
  step, full stop (walk D2 stands).
- **No new guard row, no `safeWrite` change, no `GuardAction`** — generation
  commits nothing; the append-only receipt row g and the §6.0 exception inventory
  are unchanged.
- **No auto-commit of generated assets** anywhere, under any flag. *(Rev 2:
  superseded for the author path — commit happens only behind the explicit
  in-command confirmation, never silently.)*
- **No regeneration-on-staleness** — assets, once present, are the member's to
  maintain; `--gen` exists for a fresh look.
- **No count/shape tuning flags in rev 1** — defaults only, until real usage says
  otherwise.

## 5. Build order and exit

Single milestone **IE5**, one PR, after IE4 exits. Order inside the PR:

1. `generate.ts` + unit suite (mock `AgentApi`): schema round-trip, whitelist
   rejection (`command_succeeds`, `fixture`, missing `bucket`), retry-then-fail
   loop, header + provenance lines present, near-miss prompts sourced from catalog.
2. `commands/eval.ts` wiring + command tests (injected agent/runner, per house
   convention):
   - zero assets → generator invoked, run consumes `<runDir>/generated/…`;
   - authored assets present → generator **not** invoked (spy), flow byte-identical;
   - per-kind independence (cases authored + triggers missing → only triggers
     generated);
   - `--no-gen` zero-asset run matches today's output;
   - `--gen` with authored assets evaluates the generated set and leaves authored
     files untouched (mtime/content assert);
   - generated run + `--commit` → refusal with the review-and-commit message
     (asserted against IE3's commit path once it exists — until then the existing
     stub refusal already covers it);
   - `--save` without `--working` → error; `--working --save` writes into the
     shared source with header intact; `--save` onto existing assets → per-kind
     refusal, nothing overwritten;
   - `--case` + zero authored cases → today's error, no generation.
3. Docs: README eval section gains the generation paragraph; engine spec §14 ME5
   entry marked superseded-by-this-spec.

*Exit:* `lint`+`typecheck`+`test` green; one live end-to-end on a real bare skill in
a team repo — `eval <bare-skill>` generates, runs three arms, prints a verdict and
the review instruction; `--working --save` then publish then `eval --commit` lands a
receipt whose version contains the saved cases.

**Rev 2 tests (author confirm-commit path):** author + confirm yes → generated
assets committed into `skills/<name>/evals/` via one ordinary sync commit, receipt
lands at the NEW tree hash and that tree contains the cases (assert both); confirm
no → no team-repo write, run continues on the run-tree set, no receipt, source dir
untouched; non-author + `--commit` + generated → rev-1 refusal unchanged;
non-interactive prompter → treated as no; authored-assets runs never see the
question; the arms demonstrably run at the post-commit version (assert the
receipt's `version` differs from the pre-generation head and equals
`HEAD:skills/<name>` after the sync commit).

## 6. Defaults chosen here (veto cheap)

1. Generation is **on by default** for missing kinds; `--no-gen` opts out. (The
   user-stated behavior; the old behavior remains one flag away.)
2. Per-kind independence rather than all-or-nothing.
3. `command_succeeds` excluded from the generated-check whitelist.
4. Generation failure after 2 retries fails the run (no silent empty report).
5. *(Rev 2 — resolved by Ajay, 2026-09-08, Terum a5ec5efd.)* Author path: one
   command with an explicit confirm commits generated assets into the skill and
   lands a pinned receipt (§3.2). Non-authors: generated runs never commit;
   review-then-commit remains their only path. The rev-1 alternative that broke
   §4.1 pinning (receipts without pinned cases) stays rejected — rev 2 pins by
   committing the cases first, not by weakening the receipt.
6. Counts 5/5/3 with ≥1 adversarial; not configurable in rev 1.
7. `--save` restricted to `--working`, refuses overwrite, is the only new write.
