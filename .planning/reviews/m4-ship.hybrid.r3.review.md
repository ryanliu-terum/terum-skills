# ultrareview: m4-ship

Fix-scoped confirmation pass (round 3, the last under the cap) over `67cee35` — the r2 fixes — against base `b2ec5727074b6c7a8d8894ce8c01b829f1f8d7f8`. **No critical or high findings survived verification**, so the four r1 highs and the r2 high (the credential scrub) are settled and the branch clears the bar the harden loop gates on. What remains is a consistent shape rather than a blocker: three of the r2 fixes each traded their original defect for a smaller one on the same line — `treeBetween`'s one-pass read swapped a bounded 2-child loop for an unbounded fan-out on git's blocking pre-push path; the exclusive-create reclaim swapped an always-restoring `rename` for a read-then-recreate whose `finally` destroys a live holder's record when either step fails; and the endorsed batch swapped a fresh ledger read for a snapshot with no guard against a team vanishing mid-run. Separately, two fixes were applied at one of their two sites: the `blocked()` completeness rule never reached `reconcileShared`, and `leave`'s new §8 mutex excludes hook syncs only, leaving interactive `sync` racing teardown. The new tests pin three of the four `blocked()` call sites and one of the three new stamp-gate conditions. 15 findings were confirmed 3-0; two are merged here as one defect (same root cause, adjacent branches of `reclaimStaleLock`), giving 14. 4 contested findings need human adjudication.

## Security & data-loss

- [ ] **(medium) `treeBetween`'s new one-pass read spawns one `git show` per changed skill folder with no concurrency bound, on git's blocking pre-push path** — `src/commands/guardPush.ts:110` *(merges 8 reviewer reports across Security & data-loss / Terum invariants / Correctness & tests / Reuse, simplify, perf — independently rediscovered by four dimensions)*
  The r2 "reads its blobs in one pass" fix replaced a sequential `for (const path of wanted)` loop with `await Promise.all([...wanted].map(async (path) => { const [was, is] = await Promise.all([git(['show', ...]), git(['show', ...])]); ... }))`. `git` is `(parts) => runner.run('git', parts, { cwd })` (guardPush.ts:40) and `systemRunner.run` is a raw `spawn` with `stdio: ['ignore','pipe','pipe']` (src/lib/runner.ts:14-20) — no pool, no queue. `wanted` is one `SKILL.md` per touched `skills/<folder>/` plus `team.json`, so this spawns `2 × |wanted|` children simultaneously, scaling with the size of the push. The second half of the same commit makes it worse: `systemRunner` rejects on `child.on('error')`, that propagates into the `catch` at guardPush.ts:66, and the new `pushGuardMessage` (guardPush.ts:76-80) renders it as `Push guard could not run: spawn git EMFILE. Nothing was checked, so the push is refused` with exit 1 — git aborts the whole push, and the only escape offered is `--no-verify`, i.e. running with the D12 guard off. The pre-fix loop had a fixed 2-child footprint and could not reach this.
  **Fix:** bound the fan-out — chunk `[...wanted]` into batches of ~8-16 or use a small pool — or drop the per-path spawns for a single `git cat-file --batch` fed `<base>:<path>` / `<head>:<path>` on stdin (one child regardless of push size; it already reports missing blobs as `<oid> missing`). Sibling unbounded-`Promise.all`-over-`runner.run` call sites to sweep if a limiter is added: `src/commands/search.ts:42`, `src/commands/ls.ts:41`, `src/lib/readme.ts:136`.

- [ ] **(medium) `reclaimStaleLock` destroys a live holder's lock record whenever the aside read or the exclusive re-create fails, freeing a mutex a holder still believes it owns** — `src/lib/hook.ts:217` and `src/lib/hook.ts:226` *(merges 9 reviewer reports across Terum invariants / Security & data-loss / Reuse, simplify, perf / Correctness & tests, plus one residual near-duplicate merged here: same root cause on the two adjacent failure branches)*
  The r2 rewrite (hook.ts:212-227) moves the lock aside, restores a displaced live record with an exclusive create, and removes the aside in a `finally` that also runs while an exception propagates. Two branches drop the only surviving copy of a live holder's record. **(a) Unreadable aside, hook.ts:217:** `const moved = await readFile(aside, 'utf8').catch(() => null)` collapses "the aside is gone" (ENOENT — benign; the only reachable case is `leave`'s new `removeRunArtifacts` sweep, where `path` is already held) with "the aside could not be read" (EMFILE under the fan-outs above, EIO, ESTALE, a Windows share-mode denial). On the latter the restore is skipped and the `finally` deletes the file. **(b) Failed re-create, hook.ts:226:** only `EEXIST` is tolerated; any other `open`/`writeFile` failure rethrows at line 223 and line 226 then deletes the aside. Pre-fix, both paths were `await rename(aside, path)` — metadata-only, cannot fail on a full disk, and on failure left the `.stale-*` copy for `removeRunArtifacts`/an operator. Consequence in both: `run/<team>.lock` no longer exists while holder H is mid-sync and still owns the mutex logically, so the next `sync --hook` — or `team leave`, which now takes the same mutex — acquires it freely and a second `git fetch`/`reset --hard` runs into the one clone, exactly what §8's mutex exists to prevent (spec line 381). The new case at `src/lib/__tests__/hook-mutex.test.ts:105-123` patches `fsForTests.rename` only, so it pins the EEXIST branch and the uncontested restore and exercises neither failure.
  **Fix:** never delete the aside on a path that did not re-establish or provably own the record. Read with an explicit error distinction (`ENOENT` → nothing to restore; anything else → restore or rethrow *before* the `finally` can drop it), and narrow the `finally` to the success paths so a failed re-create leaves `<team>.lock.stale-<uuid>` on disk — a name `removeRunArtifacts` and `team leave` already sweep, and which §8 documents as the killed-mid-move artifact. A cleaner primitive for the restore: `link(aside, path)` then `unlink(aside)` — atomic, fails EEXIST when a competitor took the freed path (keeping the fix's "never write over the new holder" property), preserves mtime and mode, and needs no readable content, which closes the `moved === null` hole outright. Add both branches to the mutex test via the `fsForTests` seam already used at hook-mutex.test.ts:115. Only call site: `acquireTeamLock` (hook.ts:181).

- [ ] **(medium) Endorsed batch now walks the start-of-run team snapshot, so a team removed mid-run throws ENOENT out of an un-guarded loop and fails the whole sync** — `src/commands/sync.ts:199` *(merges 4 reviewer reports across Security & data-loss / Terum invariants / Correctness & tests)*
  The fix changed `for (const [team, binding] of Object.entries((await store.read()).teams))` to `Object.entries(config.teams)` — the snapshot taken at sync.ts:64. The body calls `endorsedCandidates(store.teamClone(team), ...)` (sync.ts:201) with no try/catch, and `endorsedCandidates` → `readTeam(clone)` → `readFile(join(clone,'team.json'))` (src/lib/skills.ts:55-56) throws ENOENT when the clone is gone; that propagates to the outer handler at sync.ts:237 and the run returns `failure(...)`. Only `skipped` is consulted, and a team torn down by a concurrent `team leave` is never in `skipped`. Interactive sync takes no §8 mutex (the gate at sync.ts:73 is `if (args.hook)`) while `leave` now does, so interactive `sync` racing `team leave` is the reachable window. Concretely: terminal A syncs teams {alpha, beta}; terminal B's `team leave beta` completes after beta's refresh but before line 199; sync aborts with a raw `ENOENT ... /teams/beta/team.json`, `reconcileOrphans` never runs, and no stamp is written for alpha either — work alpha completed is discarded and reported as a failed run. The stamp loop three lines below shows the author knew teams can vanish (`!Object.hasOwn(final.teams, team)`, sync.ts:232); the endorsed loop got no equivalent.
  **Fix:** keep the snapshot as the upper bound (a team bound mid-run was never refreshed) but intersect it with a fresh read, the way the stamp loop already does — `const fresh = await store.read(); ... const current = fresh.teams[team]; if (!current?.handle || skipped.has(team)) continue;` — and wrap the per-team body in the same try/catch shape the pending loop (sync.ts:110), the placements loop (sync.ts:191) and the new hook gate (sync.ts:81) all use, so one team's disappearance costs one team.

- [ ] **(medium) `team leave`'s new §8 mutex only excludes hook syncs; an interactive `sync` still runs teardown over** — `src/commands/leave.ts:42` *(merges 2 reviewer reports across Security & data-loss / Correctness & tests)*
  `const releaseTeam = await acquireTeamLock(store.root, name); if (!releaseTeam) throw new Error('Another terum-skills sync holds the session lock on ...')` (leave.ts:42-43). The only other taker of `acquireTeamLock` is sync's gate, guarded by `if (args.hook)` (sync.ts:73-84) — a non-hook `terum-skills sync` never touches `run/<team>.lock`. So the protection the new comment claims ("a third hook could then pull into the clone being dismantled, and the running sync could place a folder back after it was removed") does not hold against an interactive sync, which is the one a user is most likely to have open in another terminal. Concretely: interactive sync is in its placement loop; leave acquires the free mutex, `removePlacements` deletes the folders and `store.update` (leave.ts:61-67) deletes `teams[name]`, the shared records and the `removedPaths` entries; sync's `place()` + `store.update` (sync.ts:176-183) then re-creates a folder on disk and rewrites a placement whose path is not in `removedPaths`. Result: a placed folder plus a `placements` entry for a team absent from `config.teams`, which no later verb owns (sync.ts:127 and `reconcileOrphans` both key off `config.teams[...]`). The clone deletion is safe — both sides hold `withCloneLock` — but the placement ledger is under no lock.
  **Fix:** take the team mutex in `sync` unconditionally (move `acquireTeamLock` out of the `if (args.hook)` gate at sync.ts:73, keeping only the `stampIsFresh` rate limit hook-only), or re-read the ledger after `withCloneLock` and re-run the placement removal for any entry of this team that reappeared, before `store.update`. At minimum, narrow the comment to say the mutex excludes hook syncs alone.

- [ ] **(low) `removeRunArtifacts`' prefix match can delete another team's live mutex, because team names may contain `.` and `-`** — `src/lib/hook.ts:239` *(merges 3 reviewer reports across Security & data-loss / Terum invariants)*
  `entries.filter((name) => name === \`${team}.stamp\` || name.startsWith(\`${team}.lock.stale-\`))`. The stamp is matched exactly, but the aside copies are matched by prefix against a user-chosen name. `teamNameSchema` is `/^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$/` (src/lib/schema.ts:15), so `a.lock.stale-b` is a legal team name. With teams `a` and `a.lock.stale-b` both joined, `team leave a` (leave.ts:58) matches `'a.lock.stale-b.lock'.startsWith('a.lock.stale-')` and deletes the second team's **live** `run/a.lock.stale-b.lock` plus its stamp — precisely what the function's own docstring promises it will not do ("The lock itself is not listed: only its holder's release removes it"). A running `sync --hook` for that team silently loses its mutex, a second hook acquires it immediately, and the first holder's release then finds a foreign record and leaves the new holder's lock in place.
  **Fix:** match the shape the reclaim actually writes rather than a bare prefix — `new RegExp('^' + escapeRegExp(team) + '\\.lock\\.stale-[0-9a-f-]{36}$').test(name)`, matching the `randomUUID()` name built at hook.ts:213. The exact-`${team}.stamp` arm is already safe.

- [ ] **(low) New hook-body comment asserts a non-zero exit is always the guard speaking, which the npx fallback branch cannot honour** — `src/lib/teamRepo.ts:361` *(merges 2 reviewer reports across Security & data-loss / Terum invariants)*
  The comment added by this fix says: "Once the launcher does run, a non-zero exit is always the guard speaking — a refusal, or its declining to permit what it could not evaluate — never a bare internal error: guardPush.run re-voices anything else." When `localPushGuardLauncher()` returns null the generated body is `if ! { command -v npx >/dev/null 2>&1; }; then ... exit 0; fi` / `exec npx -y 'terum-skills@<version>' guard-push "$@"` (teamRepo.ts:369-370). The pre-flight proves an `npx` binary exists, not that the package resolves. Because the script `exec`s, npx's status *is* the hook's status: an offline laptop, a proxy, or a registry outage exits non-zero with an npm error, git aborts the push, and `guardPush.run` — the thing that re-voices and names the `--no-verify` bypass — never ran. That is the same fail-closed-on-infrastructure the paragraph immediately above argues "would buy no safety", and it is the residue of the r1 high that the absolute-launcher fix removed only for built installs. The comment documents an invariant the code does not hold on that branch.
  **Fix:** narrow the claim to the launcher branch (or to "once `guardPush.run` is entered"), or give the npx branch the same fail-open treatment as the missing-launcher branch — run it in a subshell and, on a non-zero status that produced no guard verdict, print the "this push was NOT checked" warning and `exit 0`.

- [ ] **(low) `stripRemoteCredentials` on a remote NAME containing `@` rewrites it to `<redacted>@…`, which then goes into the git ref lookup and the printed remedy** — `src/commands/guardPush.ts:39` *(merges 2 reviewer reports across Terum invariants / Correctness & tests)*
  `args.remote` is git's `$1`, a remote **name** in the ordinary case, not a URL. `stripRemoteCredentials` (src/lib/remote.ts) rewrites only `kind === 'url'`; everything else falls through to `redact()`, documented as "lossy on purpose", which rewrites anything containing `@`: `redact('up@stream')` → `'<redacted>@stream'`. Git permits `@` in a remote name (refname rules forbid only the bare `@`). The mangled string is not confined to messages — it is interpolated into a git argument at guardPush.ts:89 via `mainOf` → `revParse(git, \`refs/remotes/${remote}/main\`)`, so the fork-point lookup for a new branch silently misses and survives only on `mainOf`'s `refs/remotes/origin/main` fallback; where that fallback is absent the push is refused with `<remote>/main could not be resolved`. Both refusals also print an unrunnable `git fetch <redacted>@stream`.
  **Fix:** scrub only what can carry a credential — `const remoteLabel = hasEmbeddedCredentials(args.remote) ? stripRemoteCredentials(args.remote) : args.remote` (both already exported from src/lib/remote.ts for exactly this "say it once" purpose), or keep raw `args.remote` for the `refs/remotes/<remote>/main` lookup and use the scrubbed value only in messages. A ref lookup should never be built from `redact()` output.

- [ ] **(low) Publish's new delete remedy names `origin` without naming the repository, and tells the user to run `--no-verify` in an unspecified checkout** — `src/commands/publish.ts:173` *(merges 2 reviewer reports across Terum invariants)*
  The reworded refusal ends `— or with \`git push --no-verify origin --delete ${branch}\`, since the push guard refuses an unattributed deletion (D12) — then retry.` `publish` takes no `--cwd` and runs from wherever the user is; the branch lives in `store.teamClone(team)`, bound to the local `clone` two lines up. The `--no-verify` clause is only meaningful inside the tool's own clone — `installPushGuard` arms `.git/hooks/pre-push` in `~/.terum/skills/teams/<team>` (teamRepo.ts:393-399), the only repository where `origin` is the team remote. Copy-pasted into the shell the user is sitting in, `origin` resolves to *their project's* remote, and `--no-verify` additionally disables whatever pre-push hooks that repo has (secret scanning, lint gates). The reworded remedy correctly explains *why* `--no-verify` is needed; it points it at the wrong working directory.
  **Fix:** interpolate the clone already in scope — `git -C ${clone} push --no-verify origin --delete ${branch}` — which makes `origin` unambiguous, keeps the bypass scoped to the clone where the D12 guard is the only pre-push hook, and matches how the message already prints an explicit remote in `where`. Update the two regexes in publish.test.ts.

## Reuse, simplify, perf

- [ ] **(medium) Blocked placements that sync can never clear now permanently withhold the stamp and print unactionable "run sync" advice every session** — `src/commands/sync.ts:138` *(merges 2 reviewer reports across Reuse, simplify, perf / Correctness & tests)*
  `blocked()` routes `Blocked ${path}: its skill is no longer in the repository.` into both `deferred` and `incomplete`. `incomplete` withholds the stamp (sync.ts:232) and `deferred.length` is rendered by the hook as ``${value.deferred.length} skills need review — run `terum-skills sync` `` (src/lib/execute.ts:40). But nothing in sync ever clears that placement: reaching line 138 requires the person file to still list the skill (sync.ts:135), so `reconcileOrphans` skips it, and no path deletes `config.placements[path]` except `uninstall` (uninstall.ts:126,131) and `leave`. So every session prints a "run sync" count that sync cannot act on, and the team is never stamped again. Before this fix the same state produced a stderr notice only.
  **Fix:** either keep this never-clearing sub-case as notice-only, or name the real remedy in the message (`terum-skills uninstall`) and keep it out of `deferred`, which execute.ts advertises as "run sync". This extends the settled fork in `.planning/debug/harden/m4-ship.deferred.md` rather than re-raising it: that entry assumes the item is clearable "until an interactive sync clears the item", which this sub-case never is. Consider `const blocked = (team, line) => { notice(line); incomplete.add(team); }` for the unclearable arm, and pin the exact `deferred` contents for at least one blocked path.

- [ ] **(low) Built-launcher assertion compares a non-realpathed tmpdir path against a path the loader realpaths** — `src/__tests__/bin.test.ts:75` *(merges 2 reviewer reports across Reuse, simplify, perf / Correctness & tests)*
  bin.test.ts:72-76 imports the built `teamRepo.js`, calls `installPushGuard`, and asserts `expect(armed).toContain(bin)`. `out` comes from `mkdtemp(resolve(tmpdir(), 'terum-bin-'))` (line 29) and is **not** realpathed, while the launcher being checked is derived inside the built module from `import.meta.url` (`localPushGuardLauncher()`, teamRepo.ts:344), which every loader on this path resolves through realpath: Node's ESM `finalizeResolution` realpaths `file:` specifiers absent `--preserve-symlinks`, and vitest inlines this file (outside node_modules) so Vite's `getRealPath` realpaths it too — no `resolve.preserveSymlinks` in vitest.config.ts. On darwin `os.tmpdir()` is `/var/folders/...` whose realpath is `/private/var/folders/...`, so the hook records `/private/var/.../index.js` and the assertion passes only because the non-real path happens to be a literal suffix. Any TMPDIR whose realpath is not a suffix of the symlinked path (e.g. `~/tmp -> /mnt/scratch`) turns this red with a confusing diff.
  **Fix:** `out = await realpath(await mkdtemp(...))` in `beforeAll`, so `bin`, the built module's `import.meta.url` and the armed hook all speak one path — which also preserves the meaning of the sibling `not.toContain('npx')` assertion. Stronger still: assert the whole generated launch line (`exec '<node>' '<entry>' guard-push "$@"`) so a differently-rooted-but-suffix-matching path fails.
