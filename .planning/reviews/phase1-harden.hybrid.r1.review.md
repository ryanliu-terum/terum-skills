# ultrareview: phase1-harden

**Verdict.** Base `0619519` predates all of `src/`, so this is effectively a first full review of the terum-skills CLI (phase 1, excluding `src/lib/evals/**`). Four reviewers filed 361 raw findings; 144 were merged as cross-dimension duplicates before verification, and 217 distinct findings went through 3-vote adversarial verification, of which **33 were confirmed** (19 high, 14 medium, no critical). The high band is not spread evenly — it clusters on three concrete classes. First, **destructive writes that overwrite work the tool did not create**: publish force-pushes an unvetted `publish/<name>-2` fallback (and force-overwrites extra commits on a reused `publish/<name>`), sync's post-rename re-place `rm -rf`s an unowned folder at the new name, `install` deletes a locally-edited owned placement instead of quarantining it, `share`'s `replaceDirectory` deletes the author's source folder outside quarantine unattended, and `refreshClone` hard-resets a clone another process holds the writer lock on — reporting the lost write as pushed. Second, **the §8 hook contract is broken in practice**: sync's pending-replay loop hands the raw stdout Prompter to `installOne`/`uninstallOne`, so plain-text notices land next to the SessionStart reload directive, and no test covers hook mode with a non-empty `pending`. Third, **durable operations get reported as failures** because their last decorative step is unguarded (`offerHook` after a completed join/create, setup's roster read-back). Separately, README generation interpolates unescaped `category`/`author` and lets skill text emit a second `terum-skills:end` marker — a poisoned README then makes *every* subsequent team-repo write throw, for every member, until someone hand-edits the repo. Three findings ended in 2-1 splits and need human adjudication; roughly 150 medium/low findings were never adversarially checked and are listed at the end unmodified.

## Security & data-loss

### High

- [ ] **publish branch-reuse test never covers a `publish/<name>` carrying the endorsement PLUS other commits — those commits are force-overwritten** — `src/commands/publish.ts:152`; test gap at `src/commands/__tests__/publish.test.ts:132` *(merges 2 reports across Security & data-loss / Correctness & tests)*
  The refusal loop only builds branches where `carriesThis === false`. The guard asks only "does their `team.json` list this ID", never "is their branch otherwise what we would produce". Once it returns, safeWrite hard-resets to `origin/main`, re-applies only its own edit, and force-pushes under a lease read from the ref it just fetched — so the push always succeeds and every extra commit (e.g. a `skills/sample/SKILL.md` fixup pushed after review) is discarded. This is exactly the loss the guard's own doc comment at `publish.ts:134-141` promises to prevent.
  *Fix:* require the branch tip to be a single commit whose parent is an ancestor of `origin/main` and whose diff touches only `team.json`; add the third loop case asserting the extra change survives.

- [ ] **publish's `-2` fallback branch is force-pushed without the reuse check, destroying another skill's endorsement branch and its PR** — `src/commands/publish.ts:51` *(merges 4 reports across Security & data-loss / Correctness & tests / Terum invariants)*
  `assertBranchReusable` guards only `publish/<name>`, but `teamRepo.ts:194-199` iterates `[branch, `${branch}-2`]` and force-pushes the fallback under a lease taken from the just-fetched ref (so it always matches). Skill names permit `foo` and `foo-2`, so `publish/foo-2` is a legitimate in-use branch. On the stale-lease path Alice's publish of `foo` replaces Bob's `publish/foo-2`; `publish.ts:92` then takes `written.pushedTo` without checking it equals `destination`, `gh pr create` returns "already exists", and Alice is handed **Bob's** PR URL as her own result.
  *Fix:* run `assertBranchReusable` over `${destination}-2` too (or move the predicate into `push()`), and assert `written.pushedTo === destination`; test a foreign commit on `publish/sample-2` surviving a forced stale-lease path.

- [ ] **`uninstall project <name>` / `uninstall member <handle>` also removes and auto-declines out-of-scope global placements** — `src/commands/uninstall.ts:128` *(merges 4 reports across Security & data-loss / Correctness & tests / Terum invariants)*
  `ledgerScopes` unions the caller's scope with **every** ledger scope for that id, unfiltered. A skill listed in `projects.product` that the user also installed globally is deleted at both scopes, stripped from both `installed` entries, and — because it is endorsed — appended to `declined`, so sync never re-offers it. The wide union is right for the bare `uninstall <ref>` case (line 46) but wrong for a scope-qualified verb. Untested: `uninstall.test.ts` never calls the `kind: 'project'` branch.
  *Fix:* give `ledgerScopes` a scope predicate and intersect for the project (and arguably member) verbs; keep the union only at line 46. Second-order: `declined` is keyed by id with no scope, so the decline should only be added when no install record for that id survives.

- [ ] **`placer.remove()` swallows any ENOENT from the fingerprint check and then hard-deletes the placement unverified** — `src/lib/placer.ts:97` *(merges 2 reports across Security & data-loss / Terum invariants)*
  The `try` spans both `snapshotSkillDirectory` **and** `moveToQuarantine`, and the catch falls through to an unconditional `rm -rf`. A file vanishing between the walk and the read (editor swap file, watcher, build step) skips verification entirely and deletes the user's modifications; a failing quarantine `rename` (e.g. sync's quarantine-clear removing the root mid-flight) degrades into a silent delete of exactly the content quarantine exists to save. Reached from `uninstall.ts:117` and `sync.ts:126` with real user data.
  *Fix:* `lstat` the destination up front and early-return if missing; narrow the catch to the snapshot call only and move `moveToQuarantine` outside the try. Same swallow shape at `sync.ts:104`.

- [ ] **`refreshClone` hard-resets a shared clone without the safeWrite writer lock — a concurrent write is silently dropped and still reported as pushed** — `src/lib/teamRepo.ts:342`
  Every other destructive touch takes the per-clone lock (`safeWrite` at :96, `leave.ts:44` via `withCloneLock`, whose comment states the reason). `refreshClone` does not, and its callers are `sync.ts:42` (run by the SessionStart hook) and `publish.ts:38`. If a hook sync resets a clone between a `share`'s commit and its push, `compromised` stays false (no lock was taken), `git push` reports "Everything up-to-date", `safeWrite` returns `{ changed: true, pushedTo: 'main' }`, the caller records success — and the commit exists nowhere.
  *Fix:* wrap `refreshClone`'s body in `withCloneLock` (or hold it across the refresh at both call sites), watching for deadlock with the nested `safeWrite`.

- [ ] **Re-installing over an owned placement silently deletes the user's local edits (no fingerprint check, no quarantine)** — `src/commands/install.ts:98` *(merges 2 reports across Security & data-loss)*
  `installOne` decides from ledger *identity* only; `entry.fingerprint` is never consulted. With `replace: true`, `placer.ts:56-62` renames the edited folder to `.old` and `rm -rf`s it. Every sibling path preserves instead: `sync.ts:105-108` quarantines a mismatch, `uninstall.ts:117` routes through `remove()`. Amplified by `install member`/`install project`, which loop `installOne` over many skills. Tests cover only the unmodified re-install and the foreign target.
  *Fix:* snapshot the destination and compare with the ledger fingerprint before `place(..., replace: true)`, quarantining drift with sync's notice; factor sync.ts:104-109 into a shared placer helper.

- [ ] **`share`'s `replaceDirectory` `rm -rf`s the author's source folder outside quarantine, unattended — and the tests pin it** — `src/commands/share.ts:229`; tests at `src/commands/__tests__/share.test.ts:220` and `:113`
  `replaceDirectory` does `cp` → `rm -rf to` → `rename`, where `to` is the user's authoring folder from `config.shared[id].source`. It is called from `reconcileShared` (`share.ts:140`, awaited by `sync` with a non-prompting Prompter) and `--keep-repo` (`share.ts:181`). The `--keep-repo` test uses a bare `ScriptedPrompter` (which throws on any `confirm`), proving the destructive branch runs with no y/N. This inverts the safe order `place()` uses and violates the stated "never delete outside quarantine" invariant.
  *Fix:* rewrite as cp-to-staging → `rename(to, aside)`/`moveToQuarantine` → `rename(temporary, to)` → delete aside, with `finally` cleanup; assert a recoverable quarantine entry in the tests.

- [ ] **`--allow-privileged` is a share-time-only gate: sync's reconciler re-mirrors `hooks/` and `.claude-plugin/` to the team repo with no gate** — `src/commands/share.ts:128` (also `:176`); test gap at `src/commands/__tests__/share.test.ts:365`
  `hasPrivilegedContent` is referenced exactly once, at `share.ts:44` (first share). `reconcileShared` re-uploads the whole tree each sync via `sourceFiles` + `mirrorToTree`, and `assertSafePath` only blocks `.git`-like segments. An author who later adds `sample/hooks/session-start.sh` publishes it silently, and every teammate receives it on their next sync — `sync.ts:97-102` only re-prompts on an `allowed-tools` hash change.
  *Fix:* run the same gate on the reconcile and `--keep-source` publish paths, printing a "re-run share --allow-privileged" notice instead; add a share → add `hooks/` → sync test asserting the repo copy is unchanged.

## Terum invariants

### High

- [ ] **Skill metadata can inject the README end marker, permanently wedging every team-repo write** — `src/lib/readme.ts:70` *(merges 2 reports across Terum invariants / Security & data-loss; same root cause as the escaping finding above, kept separate for the wedge consequence)*
  `cell()` neutralizes only newlines and pipes, so `<!-- terum-skills:end -->` in a `description` (or an unescaped `terum-category`/`author`) survives into the generated block. Generation 1 succeeds because `applyReadme` validates only the existing README; generation 2 throws on `ends === 2`. On a non-GitHub remote that throw is inside `safeWrite` (`teamRepo.ts:121-126`), so every later install/uninstall/join/share/publish fails for the whole team; on GitHub it kills the §9 Action instead. `readme.test.ts:28-35` only feeds malformed markers through the *existing* README.
  *Fix:* escape the marker literals in `cell()` (or HTML-escape `<`), route all interpolated fields through it, and post-condition `generateReadme`/`applyReadme` on exactly one BEGIN and one END in the block.

- [ ] **`sync --hook` writes plain-text lines to stdout, breaking the reload-directive contract** — `src/lib/execute.ts:7`
  `ExecuteSink.io` is a full Prompter and `src/index.ts:8` always supplies `terminalPrompter()`, whose `print` writes to stdout — but the header comment claims hook notices go to stderr. `writeHookNotices` only routes `SyncResult.notices`; anything a verb prints via `io.print` during a hook run still lands on stdout, and the hook call graph does print (`sync.ts:51/56` → `uninstall.ts:75/118`, `install.ts:102`). AGENTS.md states verbatim that `sync --hook` "prints nothing else but the reload directive on stdout".
  *Fix:* make it safe by construction — add a `hookPrompter` whose `print` goes to stderr and have the bin build `ExecuteSink.io` from it when `--hook` is set; add a hook-mode pending-uninstall test asserting stdout is exactly the directive.

- [ ] **`injectManagedFields` crashes on any SKILL.md without a `metadata:` mapping — the very branch written to handle it** — `src/lib/skills.ts:93`
  `document.set('metadata', {})` stores a plain JS object, so the next `setIn(['metadata','id'], …)` throws `Expected YAML collection at metadata` (reproduced against the repo's yaml 2.9.0). This is the primary `share` path (`share.ts:57`), and `inspectSource` only requires `name` + `description` — so `terum-skills share ./my-skill` on a stock Agent Skill fails with a raw library message. Every fixture in `share.test.ts` and `skills.test.ts` already carries a `metadata:` block, so the branch is never entered.

- **(medium / Security & data-loss) `canonicalDigest`'s `walk()` folds a literal backslash into a path separator — the exact bug this batch's fingerprint test proves was fixed in the vendored twin** @ `src/lib/skills.ts:125` — vote 2-1

- **(medium / Correctness & tests) `ls member`/`ls project` errors reject the promise instead of returning a failure Result** @ `src/commands/ls.ts:26` — vote 2-1
  `showMember` and `showProject` are `async` and signal every error by throwing (`ls.ts:47`, `:50`, `:59`). In an async function, `return <promise>` inside a `try` completes the try block before the promise settles, so the enclosing `catch` never fires — verified: `async function outer(){ try { return inner(); } catch(e){ return 'CAUGHT'; } }` with a throwing `inner` resolves to REJECTED, not `'CAUGHT'`.
