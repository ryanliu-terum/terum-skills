# ultrareview: m4-ship

Worktree: `/Users/ryanliu/Documents/Terum/terum-codex/m4-ship` (branch `m4-ship`, diff `0e0c150...HEAD`, commit cf75c73). Paths below are repo-relative to that worktree. Mode: `verify=full`, 3-vote adversarial panel; 107 raw reviewer findings → 75 merged as duplicates → 32 distinct → **22 confirmed, 1 contested**.

**Verdict.** The M4 shipment is structurally sound but the D12 clone-local pre-push guard — the one genuinely new security surface — is enforceable-in-name-only in several reachable cases, and enforces a *weaker* rule than the `safeWrite` guard it is meant to mirror. Four independent holes let a raw push through unchecked: rename collapse (`git diff --name-only` prints only a rename's destination, so another author's folder can be taken over), unconditional skip of every ref **deletion**, `continue`-on-unresolvable-base (fail-open), and arming that only ever happens on the fresh-clone branch of `ensureClone`. Separately the hook body `exec`s `npx -y terum-skills@latest`, so an offline laptop or an npm outage blocks `git push` with an npm error and no guard verdict, and every push runs whatever was last published rather than the version the user installed. On the sync side, the §8 hourly gate is correct for the *failed* case but writes the stamp after a merely **deferred** run — exactly the "rate-limiting the failure into an hour of silence" the spec forbids — and `reconcileOrphans` is the one pass that was not gated on `skipped`, so a rate-limited or clone-busy team is still read and can print notices on a run contracted to be silent. Test coverage tracks the code closely except at the guard: `PUSH_GUARD_COMMAND`, the `core.hooksPath` write, and `cloneTeam`'s arming are asserted by nothing, and the new hourly gate silently made an existing M2 walkthrough assertion vacuous.

## Security & data-loss

- [ ] **[HIGH] The pre-push hook `exec`s `npx -y terum-skills@latest`, so every raw push needs the npm registry and runs an unpinned, network-fetched build** — `src/lib/teamRepo.ts:334` *(merges 12 reports across Security & data-loss / Terum invariants / Correctness & tests / Reuse, simplify, perf)*
  `export const PUSH_GUARD_COMMAND = 'npx -y terum-skills@latest guard-push';` is baked into the hook body at teamRepo.ts:346 (`exec ${command} "$@"`). Because the script `exec`s, npx's exit status *is* the hook's, and a non-zero pre-push hook aborts the push. (a) Offline / proxied / registry outage / no npm on PATH: `npx` must resolve the `latest` dist-tag on every invocation, fails with `npm ERR! network` (or exit 127), and the push is refused with an npm error and no guard verdict — the `--no-verify` escape hatch is only ever printed *by* the guard, which never ran. (b) `@latest` is unpinned: every push runs whatever was most recently published, not the installed version. Materially worse than the `HOOK_COMMAND` convention it copies (hook.ts:10), which is `async: true` with a 60s timeout and costs nothing on failure. The team's own test already works around it (`src/__tests__/m3-setup-walkthrough.test.ts:68` passes `--no-verify`).
  **Fix:** resolve the command at install time to the running binary (`process.execPath` + the resolved bin — the seam already exists, `installPushGuard` takes a `command` override used by `bin.test.ts:70`), falling back to `npx` pinned to this package's version with `--prefer-offline`; and make the hook distinguish "guard refused" (exit non-zero, block) from "guard could not run" (warn on stderr, exit 0) — the threat model is accidents, not abuse, and `--no-verify` already bypasses it, so failing closed on infrastructure buys no safety.

- [ ] **[HIGH] Pre-push guard skips every deletion, so a raw `git push --mirror` / `--prune` / `--delete` from a team clone silently destroys teammates' branches** — `src/commands/guardPush.ts:40` *(merges 2 reports)*
  `if (ZERO_SHA.test(localSha) || !remoteRef.startsWith('refs/heads/')) continue; // a deletion, or not a branch: no content to own`. git's pre-push contract supplies `(delete) 000…0 <remote ref> <remote sha>` for every ref being deleted, so the entire deletion set short-circuits before any ownership check; `checked` stays 0, `run()` returns `success({ checked: 0 })`, the hook exits 0, the push proceeds. Deletion is the one ref update that is pure loss and the only one the guard waives. `publish/<skill>` branches hold unmerged shared skills that exist nowhere else, and `git push --prune origin` deletes exactly the remote branches the local clone lacks — every teammate's pending publish branch. On a non-GitHub remote, `git push origin :main` deletes the team's only `main`. The same `continue` also waives all non-`refs/heads/` updates, so tag pushes go unchecked. `guard-push.test.ts:63` currently pins the hole.
  **Fix:** treat a deletion as an update that must be owned — for `ZERO_SHA.test(localSha)`, diff `remoteSha` against the empty tree and run the paths through `guardRawPush` (allow `refs/heads/publish/<skill>` only when the tip's SKILL.md carries the pusher's author line); refuse `refs/heads/main` deletion outright with the `--no-verify` hint. Update the test and add a `--prune` case.

- [ ] **[MEDIUM] `git diff --name-only` without `-z` returns C-quoted paths, so the guard refuses an author's own push of a skill containing a non-ASCII filename** — `src/commands/guardPush.ts:43` *(merges 9 reports across Security & data-loss / Correctness & tests / Terum invariants)*
  `core.quotePath` defaults to true, so any path with a byte ≥ 0x80, a control char, a `"` or a `\` comes back C-quoted *including the surrounding double quotes*: `skills/mine/résumé.md` → `"skills/mine/r\303\251sum\303\251.md"`. That string fails every allow rule in `guardRawPush` (guard.ts:58-68) because of the leading `"` — `/^skills\/([^/]+)\/.+$/` does not match — so the guard refuses the author's own push. `treeBetween` (guardPush.ts:59-68) is broken twice over: `git show base:"skills/…"` cannot find the literal quoted path (both `before`/`after` undefined) and the `/^skills\/([^/]+)\//` sibling lookup never adds the folder's SKILL.md. Skill folder names are `[a-z0-9-]` (schema.ts:19) but `references/`/`assets/` filenames are unconstrained, so this is reachable with an ordinary skill.
  **Fix:** use `['diff', '--name-only', '--no-renames', '-z', base, localSha]` and `split('\0')` — the exact spelling `src/lib/teamRepo.ts:139` already uses. Sweep sibling with the same gap: `src/commands/publish.ts:182`. Add a guard-push case with an accented/emoji auxiliary filename in the pusher's own folder.

- [ ] **[LOW] `bootstrap` arms the push guard after the staging rename, outside the cleanup the catch can undo** — `src/commands/team.ts:490` *(merges 2 reports across Security & data-loss / Terum invariants)*
  `await rename(staging, clone); await installPushGuard(clone, runner);` inside a `try` whose `catch` only does `rm(staging, …)`. Before this commit `rename` was the last statement, so every failure left only `staging` to clean. Now a throw from `installPushGuard` (failed `git config core.hooksPath`, EACCES on `.git/hooks`) makes the cleanup a no-op against a vanished path: `team create` reports failure with the GitHub repo created, the scaffold pushed, an un-guarded clone left at `clone`, and `store.update` (team.ts:239) never run.

- [ ] **[LOW] `ZERO_SHA` hardcodes 40 hex zeros, so every new-branch push from a SHA-256 clone is refused with a confusing diff error** — `src/commands/guardPush.ts:11` *(merges 2 reports across Security & data-loss / Terum invariants)*
  `const ZERO_SHA = /^0{40}$/;` — in an `--object-format=sha256` repo git's null OID is 64 zeros, so the test is false for both the new-branch and deletion markers. For a new branch, `base` becomes the literal 64-zero string, `git diff <64 zeros> <sha>` exits non-zero, and line 44 throws `Push guard could not diff …: fatal: bad object` — every first push of a `publish/<skill>` branch is refused with nothing actionable. Deletions likewise fall through into a failing diff. `remote.ts` deliberately supports non-GitHub remotes (`file:`, ssh, generic), which is where sha256 repos occur.
  **Fix:** match the null OID by shape — `/^0+$/` (git's own zero-oid test is length-agnostic), or check `git rev-parse --show-object-format`; add a `--object-format=sha256` fixture case.

- [ ] **[LOW] `stampIsFresh` treats a future stamp mtime as fresh, silently disabling the hook sync until wall-clock catches up** — `src/lib/hook.ts:140`
  `return now() - (await stat(stampPath(storeRoot, team))).mtimeMs < STAMP_FRESH_MS;` — the difference is not clamped at zero, so any future mtime makes the predicate true. A VM resumed from a snapshot, a bad NTP step, or a `run/` directory copied from another machine writes a future stamp; after the clock is corrected backwards by a day, every `sync --hook` sees a negative age, reports fresh, and no-ops silently for a full day with no notice and no `deferred` entry. The existing test only moves `now` forward.
  **Fix:** `const age = now() - mtimeMs; return age >= 0 && age < STAMP_FRESH_MS;`

## Terum invariants

- [ ] **[HIGH] Push guard misses renamed-away paths: `git diff --name-only` collapses a rename to its destination, so another author's skill folder can be taken over** — `src/commands/guardPush.ts:43` *(merges 8 reports across Terum invariants / Security & data-loss / Correctness & tests / Reuse, simplify, perf)*
  `git diff` is porcelain, so rename detection is on (`diff.renames` defaults true since git 2.9) and `--name-only` prints only the **destination** of a rename pair. The source path therefore never enters `changedPaths`, never enters `treeBetween`'s `wanted` set, and never reaches `guardRawPush`'s loop (guard.ts:58). Exploit: from a team clone, `git mv skills/theirs skills/theirs-taken`, rewrite `metadata.author` to your own line, commit, push. Every file is a ≥50%-similar rename, so only `skills/theirs-taken/...` is emitted; `tree.before('skills/theirs-taken/SKILL.md')` is `undefined` and `authorOf(after) === me`, so `ownsSkill` returns true (guard.ts:101-108) and the push is **allowed** — printing `push guard: N path(s) … are yours.` — while `skills/theirs/` is deleted from main. The `safeWrite` guard does *not* have this hole (`MutableTree.changedPaths` lists the deletion and `guard()` refuses), so the clone-local half silently enforces a weaker rule than the half it mirrors. The same collapse hides any `git mv` of a teammate's aux file into your own folder.
  **Fix:** `['diff', '--name-only', '--no-renames', '-z', base, localSha]` split on `\0` — identical to `src/lib/teamRepo.ts:139` (or read `--name-status -z` and push both sides of every `R` pair). Add a guard-push regression that `git mv`s another author's skill folder with the author rewritten and asserts refusal naming `skills/theirs/SKILL.md`. Sibling sweep: `src/commands/publish.ts:182`.

- [ ] **[MEDIUM] Team mutex is unlinked by path with no ownership check, so two hook runs can hold the same team lock** — `src/lib/hook.ts:164` *(merges 9 reports across Terum invariants / Security & data-loss / Correctness & tests)*
  `return async () => { await rm(path, { force: true }); };` and the stale-recovery `await rm(path, { force: true })` (hook.ts:168) never verify the file still holds this process's `{pid, host, started}`. **A (release steals):** run A holds the lock, its sync exceeds `LOCK_STALE_MS` (first sync of a large repo on a slow link — nothing refreshes `started` while held); at t=11min B judges it stale, removes it, takes its own; A finishes and its `finally` (sync.ts:204) deletes **B's** lock; C acquires cleanly and now B and C refresh the same clone. **B (double recovery):** two hooks see the same stale lock; P1 `rm`s then `open(…,'wx')` succeeds; P2 `rm`s P1's brand-new lock and its own `open` also succeeds. Also, in `lockIsStale` the age test runs *before* the `host`/`pidAlive` checks, so a live local holder older than 10 min is declared stale regardless.   **Fix:** make release and recovery ownership-checked — re-read and compare `{pid, host, started}` (or hold the fd and compare `fstat` ino/dev) before `rm`; steal atomically via `rename(path, path + '.stale-' + randomUUID())` where only the winning renamer proceeds; consult `pidAlive` before the age test for same-host records. Add concurrent-acquirer cases to `src/lib/__tests__/hook-mutex.test.ts` (all three current tests exercise one acquirer at a time).

## Reuse, simplify, perf

- [ ] **[MEDIUM] guard-push fetches every changed blob twice, serially, though the guard only ever reads `team.json` and `SKILL.md`** — `src/commands/guardPush.ts:60` *(merges 7 reports across Reuse, simplify, perf / Terum invariants / Correctness & tests)*
  `treeBetween` seeds `wanted` with **every** changed path (plus each folder's SKILL.md) and then spawns two `git show` processes per path, awaiting each path in turn. But `guardRawPush` (guard.ts:56-69) only ever reads content for `team.json` (via `teamChangeOpenToRawPush`) and `skills/<name>/SKILL.md` (via `ownsSkill`); `README.md` and `people/<handle>.json` are matched by *name* only. Every other blob is fetched and discarded unread, and the cost is paid before the first ownership check, so a push refused on path #1 still pays for all of it. A commit adding a 60-file skill folder spawns 120 `git show` children one pair at a time (~10-20ms each) — seconds of dead wall-clock on every raw push, on top of the `npx` cold start. It also decodes every changed blob to a utf8 string (runner.ts), so binary assets are buffered for nothing.
  **Fix:** build `wanted` from what the guard actually reads — `team.json` when changed, plus one `skills/<name>/SKILL.md` per touched folder (the loop at :62 already computes those) — keeping `changedPaths` intact for iteration. If the full set is ever needed, `Promise.all` the outer loop or replace it with a single `git cat-file --batch` fed `<rev>:<path>` lines.
