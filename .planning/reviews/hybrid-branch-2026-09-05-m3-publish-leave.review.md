# ultrareview: m3-publish-leave

Worktree: `/Users/ryanliu/Documents/Terum/terum-codex/m3-publish-leave` (branch `m3-publish-leave`, base `origin/main`, 9 code/test files + spec).

**Verdict:** The feature works on the happy path, but every failure mode around *retrying* a publish is unhandled, and the branch-naming scheme is unsafe. The one high-severity finding is a real data-loss vector: `publish/<name>` is derived from the skill name with no scope, no suffix, and no existence check, then pushed with `--force-with-lease` immediately after a `git fetch` that refreshes the very ref the lease is meant to protect — so an open endorsement PR from another member is silently rewritten, and `publish.test.ts:88-97` asserts exactly that clobber as correct behavior. The medium tier is dominated by the same theme: re-running `publish` while its PR is open exits non-zero (`gh pr create` "already exists" is treated as terminal), `publish` never re-reads `policy.publish` inside the safeWrite mutation so a `push`-policy run can commit to `main` after the team flipped to `pr`, and `team leave` snapshots the placement ledger *before* a human confirm prompt and then wipes ledger keys it may never have removed from disk. Test coverage is the weak flank: the §12 walkthrough's "offered exactly once" assertion is vacuous (the second sync is non-interactive by construction, so it cannot prompt), the push-policy test never asserts the commit it creates, and the new CLI wiring test exercises only the all-flags form and throws away the `Result`. Nothing confirmed in Reuse/simplify/perf — but three of the five contested findings live there, including a plausible high (`publish` never threads the per-team PAT into git, which would break token-authenticated teams entirely); that one is one vote from confirmed and deserves a human look before merge.

## Security & data-loss

- [ ] **[HIGH] publish force-replaces an existing `publish/<name>` branch, silently rewriting an open endorsement PR** — `src/commands/publish.ts:79`
  **Evidence:** The destination branch comes from the skill name alone — `...(teamJson.policy.publish === 'pr' ? { branch: \`publish/${record.name}\` } : {})` — with no scope, no uniqueness suffix, and no check for an existing remote branch or open PR. `teamRepo.ts:181` pushes it as `git push -q --force-with-lease origin HEAD:refs/heads/${target}`, and the lease is meaningless because `teamRepo.ts:100` runs `git fetch origin` at the top of the same loop iteration, refreshing `refs/remotes/origin/publish/<name>` moments before the push — so against a pre-existing branch it behaves exactly like `--force`. `publish.test.ts:88-97` enshrines the clobber: the seed clone pushes its own commit to `refs/heads/publish/sample`, then the test asserts `expect(await originSha(..., 'publish/sample')).not.toBe(abandonedBefore)`.
  **Fix:** Before pushing, check whether `refs/heads/publish/<name>` exists on the remote (already fetched a line earlier) and either refuse with a message pointing at the existing PR, or make the branch unique (`publish/<name>-<scope>-<id8>`). Keep `--force-with-lease` for a branch this tool created, but it cannot be the only guard. The spec's justification at `.planning/specs/2026-09-05-m3-publish-leave.md:34` ("the lease fails if someone else moved it") is factually wrong given the fetch-then-push ordering and needs correcting too. `publish.ts` is the only caller passing `branch` to `safeWrite`.

- [ ] **[MEDIUM] `removePlacements` trusts a caller-supplied ledger snapshot it never re-reads, so `team leave` can wipe a placement's ledger entry while leaving the skill folder on disk** — `src/commands/uninstall.ts:78` *(merges 2 reports across Security & data-loss / Correctness & tests)*
  **Evidence:** The extracted helper operates purely on the array handed to it and deletes only the key it was given (`uninstall.ts:77-88`, `await store.update((fresh) => { delete fresh.placements[path]; })`). The original caller stayed safe by re-reading the ledger immediately before the loop (`uninstall.ts:57`, no prompt in between). The new caller does not: `leave.ts:22` computes `matching` from the snapshot read at `leave.ts:18`, blocks on `io.confirm` at `leave.ts:32`, then calls `removePlacements` at `leave.ts:36`, and finally drops every remaining team placement from the ledger without touching the filesystem (`leave.ts:47`). Scenario: user leaves the confirm prompt open while a SessionStart hook fires `sync --hook`; sync's rename branch (`sync.ts:114-122`) moves `placements[oldPath]` → `placements[newPath]`; `removePlacements` then no-ops on the stale `oldPath` (`placer.remove` ENOENT-tolerant, `placer.ts:92`), and `leave.ts:47` deletes `placements[newPath]` while the directory survives. The command prints "1 placed skill(s) will be removed." and returns `removed: 1`, but the folder stays in `~/.claude/skills`, still loaded by Claude Code and now untracked — so no later `sync`/`uninstall` can ever clean it (the ledger is the sole authority, `sync.ts:77-79`).   **Fix:** Recompute the placement list from a fresh `store.read()` *after* the confirm (mirroring `uninstall.ts:57`) — either re-read inside the helper (take a predicate rather than pre-read entries) or re-derive `matching` in `leave.ts` immediately before line 36, keeping the pre-prompt read only for summary counts. Also make `leave.ts:47` delete only paths the removal loop actually processed (return them from the helper). Sibling sites to check: `uninstall.ts:57` (currently safe) and `sync.ts:80`, which can also prompt mid-loop at `sync.ts:97-99`.

- [ ] **[LOW] `--project` with an inherited `Object` key passes the unknown-project check and crashes with a TypeError** — `src/commands/publish.ts:46`
  **Evidence:** `teamJson.projects[args.project] ? { kind: 'project', project: args.project } : (() => { throw new Error(\`Unknown project ${args.project}.\`) })()` is truthy for any `Object.prototype` key; `publish.ts:48` then does `teamJson.projects[scope.project]!.skills` and `publish.ts:50` `list.includes(record.id)`. - [ ] **[LOW] `placer.remove`'s "Refusing to remove unowned placement" guard is inert because callers pass `dirname(path)` as the target root** — `src/commands/uninstall.ts:80`
  **Evidence:** The helper derives the root from the path it is about to delete (`const root = dirname(path); ... remove(root, path, entry.fingerprint, ...)`), while `placer.ts:83-88` validates exactly that relationship (`if (dirname(destination) !== root || !isAbsolute(destination)) throw ...`). Sweep: the same `dirname(path)` + `remove(root, path, ...)` pairing appears at `uninstall.ts:80-83` (now shared by `leave.ts:36`) and `sync.ts:110-123`.

- [ ] **[LOW] `removePlacements` recreates deleted directory trees via `lockTarget`'s `mkdir -p`** — `src/commands/uninstall.ts:81` *(merges 2 reports across Terum invariants / Reuse, simplify, perf)*
  **Evidence:** The helper derives the lock root from the ledger path and locks it unconditionally (`const root = dirname(path); const release = await lockTarget(root, basename(path));`), and `lockTarget` creates the directory before taking the lock (`placer.ts:37-40`, `await mkdir(targetRoot, { recursive: true })`; the lockfile itself lives in `tmpdir()`, so the mkdir exists only for the placement root). For `install`/`sync` that is correct — they are about to write there. In a *removal* loop it is backwards: `remove()` already tolerates a missing destination, so on a stale entry the only effect is to resurrect the tree. ### Mechanical — one fix, trivial / low-risk / isolated, patch supplied; batch-apply on ONE confirmation (6)

- **medium — Re-running publish while its PR is still open exits with a failure result** — `src/commands/publish.ts:103`
  - Root cause: `gh pr create`'s exit code is treated as a two-valued signal (0 = PR opened, anything else = terminal failure), but gh uses a non-zero exit for the one outcome that means "the work is already done": when a PR already exists for the head branch it exits 1 and prints `a pull request for branch "publish/sample" into branch "main" already exists:` followed by that PR's URL. src/commands/publish.ts:97-103 has no branch for that case, so it prints the compare URL and returns `failure(...)` (non-zero CLI exit) even though the branch was refreshed and the PR is open and correct.
