---
name: ultrareview
description: In-session multi-agent code-diff reviewer. Review a branch / PR / working-tree diff across 4 dimensions (correctness & tests, security & data-loss, Terum CLAUDE.md invariants, reuse/simplify/perf) with 3-vote adversarial verification, then triage every confirmed finding into mechanical / clear / fork / declined (with a patch for the mechanical ones), emit a severity-ranked report, and auto-create bug logs for the worst findings. Use when the user wants to code-review a diff locally — the Max-included, in-session replacement for cloud /code-review ultra. Args: [<PR#>] [--working] [--no-triage] [--no-logs] + optional knobs/presets (--quick|--balanced|--in-depth|--max; --model/--review-model/--verify-model; --efficient/--verify).
---

Run the `ultrareview` multi-agent code-diff reviewer on the current branch, a PR, or your working tree, then turn its findings into a report, a triage (what to apply, what to confirm, what to decide), and (optionally) bug logs.

The workflow's canonical target/behavior args are `[<PR#>] [--working] [--no-triage] [--no-logs]`, plus the knob/preset flags below:
- (no args) → review the current branch vs `main`
- `<PR#>` → review that GitHub PR (e.g. `123` or `#123`; needs `gh` authenticated)
- `--working` → review staged + unstaged changes to **TRACKED** files (`git diff HEAD`). **Untracked/new files are NOT reviewed**, and the workflow's own warning about them never reaches the return value (it's built into the diff-acquisition prompt but dropped before the final return). If the user's phrasing implies new files ("everything I changed", "the files I added"), either tell them plainly that untracked files are excluded, or have them run `git add -N <paths>` first so the diff picks the files up.
- `--no-triage` (alias: `--no-fix`) → skip the Triage stage. **Triage runs by DEFAULT** (Ryan, 2026-09-04): after verification, one read-only agent per CONFIRMED finding investigates the root cause, lists the fix options (Depth/Cost/Wins-if), rates the recommended one on the `/single-fix` scale (difficulty / risk / scope), and supplies a unified-diff patch **only** when it is trivial + low-risk + isolated. The workflow then sorts the findings — **in code, from the ratings, never by the agent's own say-so** — into `mechanical` / `clear` / `fork` / `declined` (+ `untriaged` for an agent that died or answered unusably). It never applies anything. Skipped automatically, with a NOTE and `triage.skipped` set, on an un-checked-out PR (code can't be investigated from diff text) and on an invalid hybrid panel. It replaced the old critical/high-only fix proposer: `proposedFix` no longer exists in the return value; `triage` and `triageMarkdown` do.
- `--no-logs` → skip auto bug-log creation
- **Knobs / presets** (additive to any mode; opt-in — omit everything for today's full-depth, inherit-model behavior):
  - `--quick` / `--balanced` / `--in-depth` / `--max` (or `--preset=<name>`) — one word sets model + verification depth. In ultrareview `--in-depth` and `--max` differ only by review model (sonnet vs opus) — there is no drift stage for the drift cap to affect.
  - `--efficient[=level]` / `--verify=level` — verification depth (`full|conservative|balanced|aggressive`). `--drift` is accepted-but-ignored (ultrareview has no cross-spec drift stage).
  - `--model=<m>` / `--review-model=<m>` / `--verify-model=<m>` / `--fable-review` — pin a model per stage (`opus|sonnet|haiku|fable`); omit → inherit the session `/model`. Triage runs on the **review** model (it reads code and reasons about fixes the way a finder does).
  - `--codex-verify` is also parsed here, but it belongs to **`/hybrid-review`** (Claude finds, Codex verifies) — do not pass it from `/ultrareview`; route the user there instead. Note it also makes `--in-depth`/`--max` differ by Codex reasoning effort, not only by review model. See `.claude/skills/hybrid-review/SKILL.md`. `--fast` is the same story — parsed here, meaningful only with `--codex-verify` (it sets the Codex service tier); on its own the script logs `NOTE: --fast ignored` and runs unchanged.

## Step 0 — resolve the review target (do this BEFORE invoking the workflow)

`$ARGUMENTS` is whatever the user typed — it may already be canonical flags, OR natural language ("review PR 109 off the remote", "just my uncommitted edits", "everything I changed this session"). The workflow's own **target** parser is deliberately dumb: the review target comes from a bare PR number or `--working` and nothing else, and **any token it does not recognize is silently ignored, leaving the target at branch-vs-`main`**. (It *does* parse the knob/preset flags listed above — plus `--drift`, which it accepts and ignores with a logged NOTE, and `--codex-verify`, which is `/hybrid-review`'s entry point — and it WARNs on an unknown preset or model name. None of those change the target.) So YOU translate intent → canonical args here; never pass free text straight through and rely on that fallback.

Map the user's phrasing to one mode + optional flags:

| User intent (any phrasing) | Canonical arg |
| --- | --- |
| a specific GitHub PR ("PR 109", "pull request #109", "review 109 from the remote") | the bare number, e.g. `109` |
| uncommitted/staged work ("my working tree", "uncommitted edits", "what I haven't committed yet") | `--working` (tracked files only — see caveat above; flag if the user has new/untracked files) |
| this branch's full diff ("branch vs main", "everything since main", "all my work this session") | (no positional arg) |
| + skip triage / patches ("just the report", "no fixes", "don't investigate") | add `--no-triage` |
| + skip bug logs ("don't write bug logs") | add `--no-logs` |

Translation rules:
- A PR target needs an actual digit token (`109` / `#109`). If the user spells the number out or it's unclear which PR they mean, ASK for the number — do not guess.
- `--no-triage` and `--no-logs` are additive to any mode. Triage is ON by default.
- Empty `$ARGUMENTS` → no args (branch vs `main`). This is the ONLY case where the bare default is the intended target.
- **If `$ARGUMENTS` is non-empty but you cannot confidently map it to a row above, STOP and ask one clarifying question** (PR# / working tree / whole branch?). Do NOT let it slide into the silent branch-vs-`main` fallback — that reviews the wrong diff and the result looks clean, which is a no-silent-degradation violation.
- If the user names BOTH a PR and the working tree, the PR wins; tell them `Ignoring working-tree; reviewing PR #<n>`.

Then invoke the workflow with the **canonical** args you resolved (NOT the raw text), passing through any knob/preset flags the user gave:
`Workflow({ scriptPath: ".claude/workflows/ultrareview.js", args: "<resolved canonical args + knob/preset flags>" })`

> Use **scriptPath, not `name`**: by-name invocation shows the script content in the approval dialog and trips the Windows control-char/CRLF guard (see `.planning/specs/2026-07-21-reviewer-model-knobs.md`, R1). The relative path resolves from the repo-root cwd.

When the workflow returns:

1. If it returns `diffAvailable: false` (empty diff, not a git repo, bad PR#), surface the `error` message and STOP.

   An `error` field **without** `diffAvailable: false` is the *synthesis-failed* path (`Synthesis failed -- returning verified findings raw.`). The review, verify panel and triage already ran: `counts`, `confirmedFindings`, `contestedFindings`, `unverifiedFindings`, `stats`, `triage` and `triageMarkdown` are all populated — only `reportMarkdown` is missing. Do NOT stop. Say synthesis failed, then either skip step 2 or write the report markdown yourself from `confirmedFindings` + `triageMarkdown`, and continue with steps 3-7 normally.

2. Write the returned `reportMarkdown` to `.planning/reviews/<target>.review.md`, where `<target>` is the returned `target` field **slugified — replace `/` with `-`** (branch-mode `target` is the raw branch name, e.g. `feat/github-cheap-model`, which would otherwise create a `.planning/reviews/feat/` subdirectory; the directory is flat — every existing report there is `<slug>.review.md`). In `--working` mode `target` is the constant `"working"`, so date-suffix it (`working-YYYY-MM-DD.review.md`) rather than overwriting the previous run. Create `.planning/reviews/` if it does not exist.

   The `## Triage` section is appended to `reportMarkdown` by the workflow itself (in code, not by the synthesizer, which drops lines it is told to echo), so the saved report carries the buckets, the mechanical patches, and the forks in `/decision-walk`'s input shape — `/decision-walk <that path>` works on it directly.

3. Post an inline summary: the severity-count table (`counts` — CONFIRMED only) and `topFindings` (the critical/high items) with their `file:line`. Quote `stats.rawFindings → stats.distinctFindings` (the Dedup stage merges the same defect reported by several dimensions BEFORE verification, so each distinct finding is verified once against the union of the reviewers' evidence); a finding with `dupCount > 1` was independently rediscovered by the dimensions in `dupDimensions` — mention that, it is a confidence signal. If this was a low-confidence run (`modeDetail.preset === "quick"`, or a 1-vote verify level), say so plainly — those findings were single-verifier checked, not a trust gate. Then surface, but do NOT treat as confirmed and never fold into `counts`: any `contestedFindings` (verify panel split — need human adjudication) and `unverifiedFindings` (efficient mode skipped adversarial verification for them).

   Then the triage line, from `triage.counts`: `Triage: N confirmed → a mechanical · b clear · c fork · d declined (· e UNTRIAGED)`. If `triage.skipped` is set, say why instead (`--no-triage`, files not on disk, invalid panel, nothing confirmed) — a missing triage must never read as "nothing to do".

4. **Adjudicate — from the Triage buckets, not from scratch. Convention is NEVER a sufficient reason to decline.** The Triage stage already did the per-finding investigation and applied this step's rules (read the code at the cited line, checked the deferred register, applied the standalone test, rated difficulty / risk / scope); the bucket was then derived in code from those ratings. Your job is to check its work where a wrong call costs something, not to redo it:
   - **`declined`** — each carries a cited reason (a decline without one lands `untriaged`, never `declined`). Apply the **standalone test** yourself: *would this code be wrong or fragile if it were the ONLY place in the codebase doing it?*
     - **No → load-bearing convention** (deviating would itself be a bug, e.g. "all disconnect routes preserve state flags"). The decline stands — say *why* the consistency is load-bearing.
     - **Yes → calcified mistake** (the pattern is consistent only because the flaw propagated). Convention does not absolve it; overrule the decline and treat the finding as **clear** with a sibling-sweep worklist.
   - **`clear` with `scope: pattern`** — `triage.patternDetail` IS the sibling-sweep worklist (plus your own grep). Fix the siblings in the same change when the sweep is small (root CLAUDE.md — "**grep for every sibling call-site sharing the pattern and fix them in the same commit**"); when it is too big for this change, file a **`.deferred` bug log** (`.planning/debug/CONVENTIONS.md` — `status: deferred`, with `why_deferred` + `sweep_scope`) so it is tracked debt, not silently re-calcified.
   - **`fork`** — do NOT decide it here; that is step 6's `/decision-walk` hand-off. A fork the workflow could not settle is not yours to settle silently either.
   - **`untriaged`** — the triage agent died or answered unusably. Investigate by hand the old way (read the code at the cited line, apply the rules above), or resume the run with `resumeFromRunId` so only the dead triage agents re-execute.
   - **First check the existing `.deferred` register** (`find .planning/debug -name '*.deferred.md'`, or `grep -rl 'status: deferred' .planning/debug`): a finding already adjudicated-and-deferred there is a known decision — annotate it as deferred (cite the log) and move on, don't re-litigate it. Triage was told to do this; verify it did for anything it declined on those grounds.
   - "Pre-existing / out-of-scope for this diff" is a legitimate decline, but a fragile pre-existing pattern still earns a `.deferred` log — that is how out-of-scope flaws stop being invisible across review rounds.

   Record the disposition of every critical/high finding (mechanical-applied | clear-fixed | clear-swept | fork-walked | deferred-with-log | declined-load-bearing) in your summary so the next round/agent inherits the decision instead of re-deriving it.

5. **Auto bug-logs** — SKIP this entire step if the returned `noLogs` is true. Otherwise, for each finding in `confirmedFindings` whose `severity` is `critical` **or `high`** OR whose `dimKey` is `security` **or whose `dupDimKeys` contains `security`** (a merged finding keeps only its representative's `dimKey`, so a security report absorbed into a higher-severity correctness one is still security-eligible) (**only** `confirmedFindings` are eligible — NEVER auto-log `contestedFindings` or `unverifiedFindings`; those are surfaced for human adjudication, not treated as real defects):

   > **Threshold rationale** (Ryan, 2026-07-30): `high` was added so a confirmed high-severity correctness bug leaves a durable record and so `/parallel-fix` — which consumes *existing* bug logs — can run straight off a review instead of needing one `/single-fix` turn per finding. `medium`/`low` stay OUT on purpose: the bug corpus is an analytical asset (the invariant meta-audit read ~243 logs), and filling it with style nits degrades that. Note `/single-fix` writes its own log for anything you hand it, and dedups against existing logs — so a finding below this threshold is not lost, it just gets logged on demand rather than up front.
   a. Read `.planning/debug/CONVENTIONS.md` (canonical frontmatter + body shape) and `.planning/debug/BUG-GROUPS.md` (the current group set + overlap rules). Do NOT hardcode the schema or the group list — they drift.
   b. Classify the finding's `file` into one group per `BUG-GROUPS.md`.
   c. Get a number — run `git fetch origin` **once** first, then run the script **once per finding**: `NNN=$(bash scripts/next-bug-number.sh)`. This is the mutex-locked counter; NEVER choose a number by grepping or `ls`-ing existing logs. The fetch is not optional: the script derives its ceiling from `git log --all` + `git ls-tree` over local **and remote-tracking** refs, so a number already live on an unfetched sibling branch gets reissued — a collision that fails the required `npm run check:bug-log-status` check (`.planning/debug/CONVENTIONS.md` § Numbering).
   d. Write `.planning/debug/{group}/bug-NNN-<slug>.md` (slug = kebab of the finding title). Frontmatter per CONVENTIONS.md: `bug: NNN`, `slug`, `title` (the finding title), `group` (MUST equal the folder), `severity` (the finding's `severity` verbatim — already `critical|high|medium|low`), `status: open`, `found:` (today's ISO date), `files:` (the finding's `file`). Body sections exactly `## Symptom`, `## Root cause`, `## Fix`, `## Files`, filled from the finding's title/evidence and — now that triage ran — `triage.rootCause` / `triage.rootCauseLocation` / the recommended option's `change`.
   e. Treat each write as best-effort: if one bug log fails, continue with the rest and the report still stands.
   f. List the created bug-log paths so they can flow into `/single-fix` or `/parallel-fix`.

   Two triage-aware rules: skip a finding whose triage **decline you upheld** in step 4 — cite the deferral or the load-bearing reason in your summary instead of opening a log for a non-bug. And a `mechanical` finding you apply in step 6 gets its log **resolved in the same commit** (`status: resolved`, rename to `.resolved.md` per CONVENTIONS.md), so the corpus keeps the record without an open entry.

6. **Act on the buckets** (the default ending; this replaced "print `proposedFix`"). Print the `## Triage` section — or point at it in the saved report when it is long — under an explicit **"Triage — NOTHING APPLIED YET"** heading, then:
   - **Mechanical** (one fix clearly wins, trivial + low-risk + isolated, patch supplied) — show each patch. Ask ONE question: "Apply all N mechanical patches?" with the titles listed; the user may pick a subset. Only on an explicit yes: apply each with the Edit tool using the diff's removed lines as the exact `old_string` — if the old text does not match, re-read the file and apply by hand, never "fix up" the patch to force a match; run the repo gates (`npm run lint` / `typecheck` / `test` — whatever `package.json` defines); commit once as `fix(review): apply <N> mechanical findings from <target> review`, listing the titles in the body. A patch that fails a gate: revert it, demote that finding to **clear**, and say so. Never let a mechanical patch through on the strength of its bucket alone — the bucket came from ratings a model produced.
   - **Clear** (one fix clearly wins, not mechanical) — for each: root cause, the recommended option with its Depth/Cost and Wins-if line, the ratings, the sibling list if `pattern`. Confirm one at a time and apply with the same gates; or, when the findings have bug logs (critical/high from step 5), offer `/parallel-fix`. Medium/low without logs → `/single-fix <title>` writes its own log on demand.
   - **Forks** (no single fix clearly wins) — do NOT resolve them. Offer `/decision-walk .planning/reviews/<target>.review.md`; the Forks section is already in decision-walk's input shape (options with Depth/Cost/Wins-if and a plain-English "why it is a fork"). If the user wants to decide inline, present each fork plain-English-first per CLAUDE.md's escalation-briefing style and record their pick; never pick silently.
   - **Declined / Untriaged** — per step 4.

   Keep this AFTER step 4, always. A finished patch under a "confirmed critical" heading reads as a settled conclusion, but findings are hypotheses (root CLAUDE.md: *"Agent findings are hypotheses"*), the verify panel is known to pass false positives when its voters share a misreading, and the bucket is only as good as the ratings behind it. The Triage section is an input to your step-4 adjudication, never a substitute for it — say so in one line when you print it. If `triage.skipped` says the files were not on disk, surface that plainly rather than treating it as "no fixes needed".

7. Report the saved report path, any created bug-log paths, the commit hash of an applied mechanical batch (if any), and the `/decision-walk` command for the forks (if any).
